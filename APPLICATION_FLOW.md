This file is the detailed technical narrative; for a short, plain-language description of what the app does (no code, no jargon — readable by anyone), see `HOW_TWEGLE_WORKS.md`, also kept updated every session.

**Last updated:** 2026-08-08 (latest) — **robots.txt gap fix (Search Console)** — while reviewing the canonical-tag fix in Search Console together, the owner's Page Indexing report also showed `https://www.twegle.in/admin` under "Crawled - currently not indexed." Root cause: `robots.txt` read `Disallow: /admin/` (with a trailing slash), which only prefix-matches `/admin/...` and never actually blocked the bare `/admin` route itself (the dashboard, behind login) — so Googlebot was still crawling it. Earlier the same day, **Canonical tag fix (Search Console)** — the owner forwarded a real Google Search Console email: "New reason preventing your pages from being indexed — Duplicate without user-selected canonical." Root cause: no `<link rel="canonical">` existed anywhere on the site, so query-string variants of the same path (homepage tabs like `?tab=games`, sort toggles, search) had no declared canonical and Google had to guess. Earlier the same day, **follow-up fix: `visibilitychange` alone didn't cover in-app tab switching.** Reported directly right after the fix below shipped: switching in-app between the Games and Quizzes/Puzzles homepage tabs never picked up a change made on another device — only a full page reload did. Cause: `visibilitychange` only fires when the browser tab/app itself is hidden or shown (switched away from, minimized, backgrounded) — clicking between homepage tabs is in-page navigation, the document is visible the entire time, so the event never fires there. A reload "worked" only because a reload always re-syncs on mount regardless of any event. Earlier the same day, **fixed cross-device "already attempted" sync not appearing on an already-open tab**: reported directly — revealing a puzzle on mobile correctly showed its checkmark there, but an already-open desktop tab logged into the same account never picked it up, even after switching between homepage tabs (only a full page reload fixed it). Two causes, both fixed. First, `syncStatsOnLogin` (`statsSync.js`) only ran once, inside a `[]`-dependency `useEffect` in `UserAuthContext.jsx`'s `UserAuthProvider` — since that provider wraps the whole app and never remounts on client-side navigation, it fired exactly once per full page load and never again, so a change made on another device afterward stayed invisible without a hard reload. Second, even with a fresh sync running in the background, `hasCompletedQuiz`/`hasRevealedPuzzle` (`badges.js`) read `localStorage` directly at render time with no React state behind them, so a background write from a completed sync didn't by itself force an already-mounted `QuizCard`/`PuzzleCard` to re-render. Earlier the same day, **fixed the actual root cause behind every "it's not working, but it works if I clear the service worker" report this session**: the app never actively checked for a new deployed version on an already-open tab, relying entirely on `vite-plugin-pwa`'s default auto-injected registration script, which registers the service worker exactly once and never checks again. Browsers only check for a newer service worker on a fresh navigation, so a visitor who left a tab open (or just didn't force-reload) across a deploy kept silently running old JS — no error, nothing visibly broken, just features that looked "not fixed" when they actually already were, confirmed repeatedly by reproducing the owner's exact steps in a fresh session and having them work while their own tab still showed stale behavior. This is the same underlying cause behind the earlier "already attempted" tick not appearing, the puzzle streak fix, and the memes-removal changes all needing a manual DevTools service-worker unregister to actually show up. Fixed properly instead of asking for another manual workaround: `main.jsx` now registers the service worker explicitly via `virtual:pwa-register` (`vite.config.js` sets `injectRegister: false` so the plugin's own auto-injected script doesn't also register a second one), checking for an update every time the tab regains focus plus hourly as a baseline, and reloading the page exactly once as soon as a new worker takes control. Also added `workbox.cleanupOutdatedCaches: true` so old precached files from a previous deploy get evicted rather than piling up. This should mean every future deploy just shows up on its own, on both web and mobile, without any manual cache-clearing step ever again. ## 1. What this app is

**Twegle** — a B2C entertainment hub built to be shared on Instagram/TikTok: personality quizzes ("What's your skincare type", "Which K-pop idol position are you", etc.), friendship quizzes ("How well do you know me?"), plus bite-sized shareable content (jokes, funny lines, quotes, motivational quotes). Visitors never sign up. Content is available in English and Hindi, with more languages planned. Revenue comes from ads and affiliate links.

## 2. Who can access what

| Who | Login? | Can do |
|---|---|---|
| Quiz-taker (anyone on the internet) | **Optional** | Take any published quiz, see their result, share it — everything works fully without an account |
| Registered visitor (username+password, no email/phone) | Optional, self-service signup at `/signup` | Same as above, plus a persistent Gamer Tag and an account page (`/account`); nothing is currently gated behind login — it exists purely so a visitor can keep an identity across devices |
| Analyst (admin role) | Yes | View quizzes and analytics only |
| Editor (admin role) | Yes | Create/edit/delete/publish quizzes, view analytics |
| Super Admin | Yes | Everything Editor can do, plus create/remove other admin accounts |

Regular end-user accounts are entirely separate from the admin system (different model, different JWT `type` claim, different login pages) and self-service via `/signup` — no email or phone number is ever collected, so account recovery relies on a one-time Recovery Code shown at signup instead of an email reset link. Every admin account, by contrast, is still created by a Super Admin through the Admins page — no self-registration there.

## 3. Visitor flow (the growth engine)

```
Sees a link/story on Instagram, TikTok, WhatsApp, or finds it via search
        ↓
Lands on the homepage — language switcher (EN/HI) + category tabs:
  Quizzes | Jokes | Funny Lines | Quotes | Motivational Quotes
        ↓
Quizzes → answers 5 questions, one per screen, progress bar → result page
Jokes/Quotes/etc. → taps a card → its own shareable page
        ↓
Sees an ad slot + (later) an affiliate link relevant to the content
        ↓
Taps "📸 Share as Image" (generates a branded picture — reshares far better than a link) or the plain link/WhatsApp buttons (which now show a real title/description preview card when pasted, not just a bare URL)
        ↓
Their friends see the image or preview card on Story/Status/WhatsApp → click through → the loop repeats
```

Nothing in this flow requires an account. An anonymous ID is stored in the visitor's browser only (not tied to any personal info) purely so "how many people played this quiz" can be counted.

### Friendship quiz flow (a second, two-person loop)

```
Person A picks a friendship quiz template, answers 8 questions about themselves
        ↓
Gets a shareable link, sends it to a WhatsApp group / Instagram Story
        ↓
Person B (and C, D, ...) opens the link, guesses what A would say — no peeking
        ↓
Sees their own score (e.g. "6/8") + a right/wrong reveal per question
        ↓
Shares THEIR score (own shareable link) → pulls more people back to A's original link
```

This is a second, independent growth loop alongside the main one above — the same link can be replayed by many different friends, each generating their own shareable result, so one person setting up a quiz can drive repeated waves of traffic rather than a single share.

### Compare-with-a-friend flow (a third loop, on the regular quizzes)

```
Person A takes any regular personality quiz, sees their own result as usual
        ↓
Taps "🆚 Compare with a friend", enters their name → gets a shareable link
        ↓
Person B opens the link — sees who invited them, NOT the result (no peeking/bias)
        ↓
Person B takes the same quiz for real
        ↓
Both results reveal together, side by side, with a match / no-match banner
        ↓
Person B shares the comparison result → pulls more people into the same quiz
```

Unlike the friendship-quiz loop, both people take the *real* quiz and get a *real* personality result — this only works on the regular single-player quizzes, reusing the exact same quiz-taking screens rather than a separate flow.

### Two-player Tic-Tac-Toe flow (a fourth loop, on the Games side)

```
Person A opens Tic-Tac-Toe, taps "🆚 Challenge a friend to a real match"
        ↓
Enters their name → gets a shareable link, is always X, always goes first
        ↓
Person B opens the link, enters their name → joins as O
        ↓
Real alternating turns — each move is submitted to the backend, checked, and
the board updates for whoever's turn it becomes next
        ↓
Game ends (win/draw) → both sides can share the result
        ↓
Loser (or the drawer) shares "beat me/drew with me — think you can do better?" → pulls more people in
```

The only growth loop so far that's genuinely turn-based rather than "both people play independently, then reveal" — no accounts, so each browser just remembers its own role (X or O) in `localStorage` for that match's code (see `FRONTEND.md`).
