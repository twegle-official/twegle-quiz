# Frontend — What's Been Built

**Status:** Working — public site and admin panel both run against the real backend/database

## How to run it

```bash
cd frontend
npm install
npm run dev
```

Opens at whatever local address Vite prints (usually `http://localhost:5173`). Requires the backend to be running too (see `BACKEND.md`) — the frontend talks to it via `VITE_API_URL` in `.env` (defaults to `http://localhost:4000/api`).

## Shareable images (📸 Share as Image)

A plain link dies in a WhatsApp/Instagram Story — a real image gets reshared. Every quiz result and post now has a "Share as Image" button that generates a branded 1080×1920 (Story-ratio) PNG — emoji, title, description, and a "Twegle" logo badge, colored to match the quiz/category gradient — and either opens the phone's native share sheet (straight to Instagram Story/WhatsApp on mobile) or downloads the file (desktop, or browsers without file-sharing support).

- `src/utils/shareImage.js` — draws the card directly with the **Canvas 2D API** (`fillRect` for the gradient, `fillText` with manual word-wrapping for text, arc/text for the logo badge), then exports it with `canvas.toBlob()`.
- **Why not a DOM-screenshot library:** the first implementation used `html-to-image` (renders the DOM as an SVG `foreignObject`, loads that as an `<img>`, then draws it to canvas). That trick is a well-known source of cross-browser flakiness, and it hung indefinitely with no error at all during testing — confirmed down to a minimal red `<div>` failing the same way, ruling out anything specific to our card's content. Canvas 2D drawing has none of that fragility and is standard, reliable behavior on every browser, including mobile Safari — the primary target for this feature. `html-to-image` was removed from the project entirely.
- Gradient colors for canvas are a small hex lookup (`GRADIENT_COLORS` in `shareImage.js`) keyed by the same Tailwind gradient strings used everywhere else — keep it in sync if a new gradient is ever added to `gradients.js`.
- **No link in the shared image (fixed 2026-08-09):** reported directly with a real shared image (a level-up card) — the picture itself carried no URL at all, since `navigator.share`'s accompanying `text`/`title` is frequently dropped entirely by the receiving app when sharing a file (Instagram/WhatsApp Stories in particular only post the image, not the caption). `drawLogo()` (shared by every card type — level-ups, quiz/post results, compare cards) now also renders "twegle.in" in a smaller line directly under the "Twegle" wordmark, baked into the image pixels so the link survives regardless of what the receiving platform does with share text. Every caller's `shareMeta.text` (the native-share caption, used when a platform *does* respect it — WhatsApp, for instance) was also given the actual page URL to share (`Result.jsx`/`PostView.jsx`/`CompareResult.jsx` reuse their existing per-item `shareUrl`; `Badges.jsx`/`BadgeToast.jsx` use `window.location.origin` since a level-up isn't tied to one specific page). Verified by patching `HTMLCanvasElement.prototype.toBlob` to capture the generated image, rendering it into an offscreen canvas, and sampling pixels in the "twegle.in" region — confirmed white text pixels present there versus the surrounding gradient.

## Link previews

`getQuizShareUrl`/`getPostShareUrl`/`getFriendshipShareUrl`/`getFriendshipResultShareUrl` in `api.js` build URLs pointing at the backend's `/api/share/...` routes rather than the React page itself — the "Copy link" and WhatsApp buttons in `ShareButtons` use whichever one is passed in as `url`. Full explanation of why (client-side apps can't set meta tags in time for link-preview crawlers) is in `BACKEND.md`. The "Share as Image" feature is unaffected by this — it shares an actual image file, not a link.

## SEO

A different problem from link previews above — Google's crawler does execute JavaScript and reads the rendered page, so unlike the WhatsApp/Instagram crawler problem, standard per-page `<title>` and meta description genuinely help here.

- **`src/utils/useDocumentMeta.js`** — a small hook (`useDocumentMeta(title, description)`) that sets `document.title` (as `"<title> | Twegle"`, falling back to the site default while data is still loading) and the `<meta name="description">` tag's content, resetting both back to the default on unmount. Wired into every content page: `Quiz`, `Result`, `PostView`, `Browse`, `FriendshipSetup`, `FriendshipPlay`, `FriendshipResult`, plus static titles on `About`/`Privacy`/`Terms`. No new dependency (no `react-helmet` or similar) — the app only ever needs to touch two tags, so a tiny hook does the job.
- **`Home.jsx`** renders minimal `WebSite` JSON-LD structured data (name, url, description) directly as a `<script type="application/ld+json">` — the one piece of structured data that actually fits cleanly; schema.org has no good native type for a personality-quiz result, so more elaborate structured data per quiz wasn't worth forcing in.
- **`Home.jsx`** also renders an `AdSlot` below the active tab's content grid, once it's non-empty (2026-08-05) — every other `AdSlot` usage sits on a result/detail page, so the homepage (the highest-traffic page) previously had no ad placement at all.
- **`frontend/public/robots.txt`** — a plain static file (allows all crawlers, blocks `/admin`, points to the sitemap). Originally read `Disallow: /admin/` (with a trailing slash) — a real gap, since that only prefix-matches `/admin/...` and doesn't block the bare `/admin` route itself (`App.jsx`'s dashboard route, behind login). Search Console's Page Indexing report surfaced `https://www.twegle.in/admin` as "Crawled - currently not indexed," which is how this was caught; fixed by dropping the trailing slash so the rule prefix-matches both `/admin` and everything under it. Done 2026-08-08.
- **`VITE_SITE_URL`** (new env var, `.env`/`.env.example`) — the frontend's own public URL, used only for the `WebSite` schema's `url` field. Defaults to `http://localhost:5173` for local dev.
- **`CanonicalLink` (`App.jsx`)** — added 2026-08-08 after Google Search Console flagged query-string variants of the same page (e.g. `/?tab=games`) as "Duplicate without user-selected canonical," since no canonical tag existed anywhere on the site. Mounted once alongside `ScrollToTop`, it keeps a single `<link rel="canonical">` tag in `<head>` in sync with `useLocation().pathname` on every route change — deliberately ignoring the query string, so every `?tab=`/`?sort=`/`?q=` variant of a path declares the same bare-path URL as canonical, matching the clean URLs `sitemap.xml` already lists. `index.html` carries a static `https://www.twegle.in/` fallback for the instant before React mounts.
- **`sitemap.xml`** itself is generated by the *backend* (`GET /sitemap.xml`, not called by the frontend at all) since it needs live database content — see `BACKEND.md` for the generation logic and the one-time hosting rewrite it'll need once frontend/backend are on separate real domains.

## Friendship quizzes ("How well do you know me?")

The one genuinely new interaction pattern on the site — every other quiz type is single-player, this one is two-sided:

1. **`FriendshipSetup.jsx`** (`/friendship/:slug`) — fetches the question template, then a single-page form: a name field plus every question shown at once with tappable option buttons (not a multi-step wizard like the regular quiz flow — filling in known facts about yourself benefits more from being able to see/edit everything than from a dramatic one-question-at-a-time reveal). On submit, calls `createFriendshipInstance` and — without navigating away — swaps the same page into a "Your link is ready!" screen with `ShareButtons` pointed at the new shareable link.
2. **`FriendshipPlay.jsx`** (`/friendship/play/:code`) — a friend opens the link, sees the subject's name and the same questions (answers withheld by the backend, not just hidden in the UI), fills in their own name + guesses, and submits. On success, navigates to `/friendship/result/:attemptId` using the ID the backend just generated, so the result becomes a real, refreshable, shareable URL rather than transient state.
3. **`FriendshipResult.jsx`** (`/friendship/result/:attemptId`) — the score reveal: big `score/total`, a message that scales with how well they did, `ShareButtons` for posting their own score (which pulls more people back to the same `/friendship/play/:code` link — this loop is the actual growth mechanic), and a full per-question breakdown (✅/❌, what the subject picked, what the friend guessed).

`FriendshipQuizCard.jsx` is the homepage-tab card, linking to the setup page — separate from `QuizCard.jsx` since it shows a different stat ("N friends have guessed" instead of "N took this") and links to a different first step.

4 starter templates are seeded (2 English + 2 Hindi) via `npm run seed:friendship-quizzes` on the backend — see `BACKEND.md`.

## Compare with a friend (regular quizzes)

Brings the friendship-quiz's "share a link, friend plays too" growth loop to the regular single-player personality quizzes, without adding a new quiz-taking flow:

1. **`Result.jsx`** — after seeing their own result, a "🆚 Compare with a friend" button reveals an inline name field (same swap-the-page-in-place pattern as `FriendshipSetup.jsx`'s share screen); submitting calls `createQuizCompare` and shows a "Your link is ready!" panel with `ShareButtons`.
2. **`CompareInvite.jsx`** (`/quiz/:quizId/vs/:code`) — a friend opens the link and sees who invited them and which quiz, but **not** the first person's result (withheld server-side — see `BACKEND.md` — so it can't bias their answers). They enter their own name and tap "Take the Quiz," which navigates into the *existing* `Quiz.jsx` flow with the compare code/name passed via router state (`navigate(path, { state })`), so the actual quiz-taking UI is 100% reused, not duplicated.
3. **`Quiz.jsx`** — reads `location.state.compareCode`/`compareName`; on the last question, if a compare code is present, it submits the result to `joinQuizCompare` instead of navigating to the normal `/result/:quizId/:resultKey` page, then navigates to the reveal page. If the link turns out to be invalid/expired, it silently falls back to the normal result page rather than dead-ending the player.
4. **`CompareResult.jsx`** (`/quiz/:quizId/vs/:code/result`) — the reveal: both people's emoji/title side by side plus a match/no-match banner, `ShareButtons`, and an `AdSlot`. If opened before the friend has played (e.g. the first person checking back on their own link), shows a "Still waiting on your friend!" state instead. Opening an already-completed link's invite page (`CompareInvite.jsx`) auto-redirects straight here.

Reuses `generateUniqueCode`'s exact approach from the friendship-quiz feature (short random `code`, not a database ID) and the same `/api/share/*` link-preview pattern for WhatsApp/Instagram previews (`getQuizCompareShareUrl`).

## Non-personality (right/wrong) quizzes

Every quiz so far mapped answers to a personality result key, tallying which key got picked most. Right/wrong quizzes (`quiz.type === 'trivia'` — an internal code label, never shown to a user; user-facing text always says "right/wrong quiz") are scored numerically instead — built to reuse as much of the existing quiz-taking flow as possible rather than a parallel UI:

- **`Quiz.jsx`** — the same per-question `handleAnswer` and `scores` tally used for personality quizzes works unchanged for a right/wrong quiz, because its option's `result` field is just the literal string `'correct'` or `'incorrect'` (see `BACKEND.md`) — so `scores.correct` already holds the right numeric score with zero new tallying code. The only real branch is at the *end*: `pickTriviaResult(quiz, scores)` finds whichever result's `minScore`-`maxScore` range contains the score, instead of `pickWinningResult` picking the most-tallied key. The score and question count are passed to the Result page via router state (`navigate(path, { state: { score, total } })`).
- **`Result.jsx`** — reads that router state to show "You scored X/N!" above the result title. Deliberately **not** load-bearing: a cold visit to a shared result link has no router state (it's only set by an in-app `navigate()` call), so the line simply doesn't render then — the result's own authored title/description still convey the tier either way, same graceful-degradation pattern already used for the compare-with-a-friend `compareCode`/`compareName` state.
- **`QuizForm.jsx`** (admin) — a "Quiz Type" dropdown ("Personality (answers → a result)" / "Right/Wrong (answers scored, not a personality result)") changes two things further down the same form: each answer option's "Pick result..." dropdown becomes a plain "Correct" checkbox (setting `result` to `'correct'`/`'incorrect'` directly), and each Result entry gains Min/Max score number inputs alongside the existing key/emoji/title/description fields. No separate authoring page for the second type — same form, same fields, just relabeled and re-typed based on the selected Quiz Type.

## Games

A new content type, but a different shape from Quiz/Post/FriendshipQuiz — a game isn't admin-authored data, it's code, so there's no admin CRUD and no fetch-by-slug from a database. Instead:

- **`src/games/registry.js`** — a plain static array (`{ slug, title, emoji, gradient, description, players }`), one entry per game. `players` is `['single']`, `['friend']`, or both — which modes a game supports (single-player vs AI/house, and/or a real friend, live or async) — and powers the "Single Player"/"2 Player" filter chips on the homepage Games tab (`Home.jsx`'s `GAME_CATEGORIES`, filtered client-side since this list isn't database content). Adding a new game means adding an entry here, a component in `src/games/`, and a case in `Game.jsx`'s render switch — no backend or admin work required for the game itself.
- **Landing on the right mode from the "2 Player" filter** — Tic-Tac-Toe supports both modes, but its page (`Game.jsx`) defaults to the single-player board with "Challenge a friend" as a small toggle link below it. Arriving from the homepage's "2 Player" filter already signals which mode the visitor wants, so `GameCard.jsx` appends `?mode=friend` to the link for any game with `'friend'` in `players` while that filter is active, and `Game.jsx` reads that query param to initialize `showChallengeForm` as `true` instead of `false` — skipping straight to the challenge form, same as Connect Four (which has no single-player mode to skip past in the first place). Plain links/direct visits (no query param) keep the original single-player-first default.
- **`src/games/TicTacToe.jsx`** — the first game. Human is always X and always goes first; the AI (O) uses a full minimax search (small enough state space — 9 cells — to brute-force with no pruning) so it plays perfectly; the best a human can do is draw. Ties between equally-good AI moves are broken randomly so it doesn't always open the same way. The AI's move fires after a short delay so it doesn't feel instant. Calls `onGameEnd('win'|'loss'|'draw')` once when the board ends, and `onReset()` when "Play again" is clicked (letting the parent page clear its own end-of-game state — see the bug note below).
- **`src/games/RockPaperScissors.jsx`** — the second game. Deliberately uses a uniform-random AI pick rather than any "smarter" logic: a single round of RPS carries no information to exploit (unlike Tic-Tac-Toe, a solved perfect-information game), so random is the fair baseline, not a corner cut. Same `onGameEnd`/`onReset` contract as `TicTacToe.jsx`, so `Game.jsx` didn't need any changes beyond a registry entry and a render-switch case to support it.
- **`src/games/MemoryMatch.jsx`** — flip-and-match card pairs (6 emoji pairs, 12 cards). No adversary and no lose condition (untimed), so it only ever reports `onGameEnd('win')`, once all pairs are matched.
- **`src/games/Game2048.jsx`** — the standard 2048: a 4x4 grid, arrow-key or on-screen-button moves, tiles slide and merge via the well-known "transpose/reverse, then always slide left" trick (four directions reduce to one merge algorithm instead of four separate ones). Win at a 2048 tile, loss when the board is full and no direction changes it.
- **`src/games/WordGuess.jsx`** — a word-guessing game, deliberately named (and drawn) without any hangman/gallows imagery — just a shrinking heart/life counter — to stay consistent with the site's family-friendly tone. A small on-brand word list (TWEGLE, VIRAL, MEME, etc.), 6 lives, win on completing the word before lives run out.
- **`src/games/GuessTheNumber.jsx`** — "the house" picks a secret 1–100, the player gets higher/lower hints, 7 attempts (enough for a binary search over that range). A good example of a game with a real win/loss condition despite having no visible "opponent" to react to your moves.
- **`src/games/Sudoku.jsx`** — a 9x9 grid, medium difficulty (36 given clues). No puzzle database or backtracking solver needed: every puzzle starts from one closed-form solved grid (`((r*3 + Math.floor(r/3) + c) % 9) + 1`), then gets scrambled via the standard Sudoku symmetry operations — relabeling digits 1-9 with a random permutation, shuffling rows within each band of 3 and columns within each stack of 3, shuffling the 3 bands/stacks themselves, and a 50/50 transpose — all of which preserve the "each digit exactly once per row/column/box" property, so the result is always a genuinely valid, varied solved grid without ever needing to verify it. Blanking out 45 of the 81 cells (reusing the existing `shuffleArray` utility from `utils/shuffle.js`) produces the puzzle; solution-checking is a plain equality comparison against the grid used to generate it, not a general Sudoku validator. Live conflict highlighting (a cell turns red if its value duplicates another in the same row/column/3x3 box) uses a straightforward `hasConflict(grid, r, c)` check. No lose condition, same as Memory Match — only ever reports `onGameEnd('win')`, once every cell is filled and matches the solution. Supports both clicking a number-pad button and typing 1-9/Backspace on the keyboard once a cell is selected.
- **`src/games/SimonSays.jsx`** — the classic growing-sequence memory game: 4 colored pads, the app flashes an ever-longer pattern, the player repeats it by clicking. Endless in principle, so it's given a real "win" state by treating reaching round 10 as mastering it (same milestone-framing idea 2048 already uses for hitting the 2048 tile) — a wrong click before then ends the game as a loss, score being however many rounds were reached either way.
- **`src/games/WhackAMole.jsx`** — a fixed-time (20s) reaction game: one mole pops up at a time in a random hole of a 3x3 grid for under a second, click it before it ducks back down. Score is moles whacked in the window; reaching 15 is framed as a win, anything less a loss (same milestone-framing pattern as Simon Says).
- **`Game.jsx`** (`/games/:slug`) — looks up the slug in the registry, renders the matching game component, and once it ends: records the anonymous outcome via `recordGamePlay`, shows `ShareButtons`, and an `AdSlot`. Share text is per-outcome and, since not every game frames itself as "beating the house" (a solo memory game or 2048 has no opponent to beat), per-game: a `SHARE_TEXT_OVERRIDES` map lets Memory Match/2048/Word Guess/Guess the Number/Sudoku/Simon Says/Whack-a-Mole supply their own win/loss phrasing, falling back to the original "beat the house" wording (`DEFAULT_SHARE_TEXT`) for Tic-Tac-Toe/Rock Paper Scissors, which are explicitly framed that way.
- **Sound effects (2026-08-08)** — `src/utils/sound.js` synthesizes three short tones (click/win/lose) on the spot with the Web Audio API rather than shipping recorded audio files — no assets to host, same zero-infrastructure-cost reasoning already used for Stories' read-aloud (Web Speech API) instead of paid TTS. Muted by default (`localStorage['twegle-sound-muted']`, opt-in, not a surprise blast of noise on first tap); `Game.jsx` gained a 🔊/🔇 toggle next to the Back button (same pattern as `ThemeToggle`), plays `win`/`lose` centrally from `handleGameEnd` (one wiring point covers all nine games), and plays `click` from a single click listener wrapped around the whole game-rendering area that checks whether the click landed on a `<button>` — covering every game's actual interactions (a cell, a card, a number-pad key, a pad) without touching any of the nine individual game components.
- **`GameCard.jsx`** — the homepage-tab card, styled identically to `QuizCard.jsx` ("N played" badge instead of "N took this"), fed by merging the static registry with `GET /api/games/counts` on the homepage.
- **`GameLeaderboard.jsx`** — the score-saving form shown after a scored game ends (Guess the Number's tries, 2048's tile, etc.). Reads `useUserAuth()`: logged-in visitors see "Saving as {Gamer Tag}" instead of a nickname field and submit with one click; guests keep the original manual "Your nickname" input. Either way, the submitted name is just a string on the score record — no account linkage beyond that.

**Bug caught during testing:** clicking "Play again" correctly reset the board, but `Game.jsx`'s own `outcome` state (which controls whether the share buttons show) didn't know the game had restarted, so the *previous* round's share buttons stayed visible over a fresh game. Fixed by having `TicTacToe` also call an `onReset` prop when the board clears, which `Game.jsx` uses to clear its own `outcome` state back to `null`.

## Two-player Tic-Tac-Toe

A real match against a friend, separate from the single-player-vs-AI `TicTacToe.jsx` above — reached via a "🆚 Challenge a friend to a real match" link shown only on the Tic-Tac-Toe game page (`Game.jsx`, `game.slug === 'tic-tac-toe'`).

- **No accounts, so no server-side notion of "which browser is X."** Filling in the challenge form calls `createTicTacToeGame(name)`, which creates the match (the creator is always `X`) and immediately writes `localStorage['tictactoe-role-<code>'] = 'X'` *before* navigating to `/games/tic-tac-toe/:code` — that's the only place a role ever gets assigned as `X`. A friend opening the invite link has no such key yet, so `TicTacToeMultiplayer.jsx` shows a join form instead of a board; submitting it calls `joinTicTacToeGame` and writes `role = 'O'` the same way. From then on, revisiting that URL in that browser always resumes with the right role, no login needed.
- **Live, not polling.** This originally polled `GET /api/tictactoe/:code` every 4 seconds; once Connect Four proved a socket.io layer end-to-end, this page was converted to the same live approach — mirrors `ConnectFourMultiplayer.jsx`'s effect almost exactly (connect `ticTacToeSocket` from `src/utils/socket.js`, emit `joinRoom { code, role }`, listen for `gameState`), just for a 3x3 board and X/O instead of a 7-column board and red/yellow. No `POLL_INTERVAL_MS` or `setInterval` anywhere in this file anymore.
- **Making a move** (`handleCellClick`) is guarded three ways before it even emits — a role must exist, the cell must be empty, and it must actually be that role's turn — then emits `makeMove { code, role, cell }` over the socket and waits for the resulting `gameState` broadcast; the backend is the real authority on whether the move was legal (see `BACKEND.md`). A `movingRef` guard (same idea as Connect Four's `droppingRef`) blocks a double-click from firing two moves before the first one's response lands.
- The board/status UI reuses the same 3x3 grid styling as the single-player `TicTacToe.jsx`, and `ShareButtons` at two different moments: while `status === 'waiting'` (send the invite), and once `status === 'finished'` (share the result, phrased from that browser's own role's perspective — "I beat Bob," "I drew with Bob," or "Bob beat me — think you can do better?").
- **Rematch** — a "🔁 Rematch" button above `ShareButtons` once `status === 'finished'`, emitting a `rematch` socket event with `{ code, role }`; the resulting `gameState` broadcast resets the board on both screens with no new link needed (same code stays in the URL).

## Single-player Connect Four

Added 2026-08-12, mirroring `TicTacToe.jsx`'s pattern exactly — `src/games/ConnectFour.jsx`, human always `red` and always goes first, AI is `yellow`, a short delay before the AI's move so it doesn't feel instant, `onGameEnd`/`onReset` contract unchanged. The one real difference from Tic-Tac-Toe is the AI itself: Tic-Tac-Toe's 9-cell board is small enough to brute-force with plain minimax, but Connect Four's 7×6 board isn't, so this uses **minimax with alpha-beta pruning at a fixed depth of 5**, scoring non-terminal positions at the depth cutoff with a standard windowed heuristic (every possible horizontal/vertical/diagonal 4-cell line scored by how many AI vs. human discs it holds, plus a small center-column bias, since center discs sit in more winning lines than edge ones) — a well-documented, standard approach for this game. Board/win-check logic (`checkWinner`, gravity-based column drops) is a standalone client-side copy of the same algorithm the backend's live multiplayer version uses (`backend/src/utils/connectFour.js`), since this game never talks to the server at all.

Before this, Connect Four's `Game.jsx` section always rendered the challenge-a-friend form (`showChallengeForm || game.slug === 'connect-four'`), since there was no single-player mode to default to. Now it follows the exact same pattern as Tic-Tac-Toe: single-player is the default, "🆚 Challenge a friend to a real match" is a secondary link, and arriving via the homepage's "2 Player" filter (`?mode=friend`) still skips straight to the challenge form.

**Bug caught in the process:** `'connect-four'` was missing from the backend's `GAME_SLUGS` allowlist (`gameController.js`), which `engagementController.js` also uses to validate `content_type: 'game'` for view/share tracking — meaning Connect Four's page-view engagement had been silently 404ing ever since Connect Four itself shipped (both single- and 2-player). Fixed by adding it to the allowlist, which fixed both the new single-player play recording and the pre-existing broken view tracking in one change.

## Live two-player Connect Four

Twegle's first real-time feature — both players see every move the instant it happens, no polling `setInterval` anywhere in this page. Reached via the same "🆚 Challenge a friend" link the single-player page above shows, or directly via the homepage's "2 Player" filter.

- **`src/utils/socket.js`** — one shared `socket.io-client` instance per namespace (`connectFourSocket` for `/connect-four`, `ticTacToeSocket` for `/tic-tac-toe`), each created once with `autoConnect: false` so a component decides exactly when to join rather than a connection opening on import. Re-mounts (navigating away and back, React StrictMode's double-invoke) reuse the same instance instead of opening duplicate sockets.
- **`ConnectFourMultiplayer.jsx`** (`/games/connect-four/:code`) — same role-remembering approach as `TicTacToeMultiplayer.jsx`: `localStorage['connectfour-role-<code>']` is `'red'` (creator, set the moment `Game.jsx`'s challenge form succeeds) or `'yellow'` (set the moment the join form succeeds). No saved role + `status === 'waiting'` shows the join form instead of a board. On mount, one `GET /:code` REST call renders the page immediately without waiting on a socket handshake first; then the socket connects, emits `joinRoom { code, role }`, and every subsequent `gameState` event from the server just replaces local state directly — there's no poll to schedule or clear, unlike the Tic-Tac-Toe page's `POLL_INTERVAL_MS` effect. If the socket drops and reconnects (phone loses signal, Render's free tier waking from a cold start), the `connect` event fires again and the page re-joins the room, which resyncs it from the server's real Mongo-backed state — the same recovery a fresh page load would give, just automatic.
- **Dropping a disc** (`handleColumnClick`) just emits `dropDisc { code, role, column }` over the socket and waits for the resulting `gameState` broadcast — there's no optimistic local update, since the server computes the landing row and win/draw check anyway and broadcasts back near-instantly. A `droppingRef` guard (same idea as Tic-Tac-Toe's `movingRef`) blocks a double-click from firing two drops before the first one's response lands.
- **Board rendering** is a 7-column × 6-row grid inside a blue "frame" (mirroring a physical Connect Four board), red/yellow circles for filled cells, white/gray-800 for empty — clicking a column (not an individual cell) drops into whichever row gravity lands it in, matching the backend's `findLandingRow`. A column is disabled once its top cell is filled or it isn't the viewer's turn.
- `ShareButtons` appears at the same two moments as Tic-Tac-Toe's: `status === 'waiting'` (send the invite) and `status === 'finished'` (share the result from that browser's own role's perspective). A "🔁 Rematch" button sits above it once finished, same `rematch` socket event pattern as Tic-Tac-Toe's.
- **`api.js`** gained `createConnectFourGame`, `fetchConnectFourGame`, `joinConnectFourGame`, `getConnectFourShareUrl` — REST-only, mirroring the Tic-Tac-Toe equivalents; there's no `makeConnectFourMove` since moves never go over REST.

## Snake and Ladder

Added 2026-08-12 with both single-player and live 2-player built together from day one, unlike Connect Four (which launched friend-only and got a single-player AI added afterward). Traditional numbered 10x10 board — square 1 at the bottom-left, rows zigzagging upward — with a fixed, generic (non-copyrighted) set of ladder/snake jump squares.

- **`src/utils/snakeLadderBoard.js`** — the shared board data (`LADDERS`, `SNAKES`, `JUMPS`), `computeLanding(position, roll)` (a roll that would overshoot square 100 just doesn't move the token — classic "exact roll to finish" rule), and `buildBoardGrid()` (builds the zigzag numbering as 10 rows, top row first, for rendering). Duplicated by hand in `backend/src/utils/snakeLadder.js` for the exact same reason `ConnectFour.jsx`'s win-check logic is duplicated from the backend — single-player never talks to the server, so it needs its own copy of the rules.
- **`src/games/SnakeLadder.jsx`** — single-player vs. "the house." Unlike Tic-Tac-Toe's minimax or Connect Four's alpha-beta search, the AI has no real decision to make here (rolling is the only action any turn), so it just rolls randomly on a short delay, same visual pacing as the other two AIs. Same `onGameEnd`/`onReset` contract as every other game component.
- **`SnakeLadderMultiplayer.jsx`** (`/games/snake-ladder/:code`) — same live pattern as `ConnectFourMultiplayer.jsx`: `localStorage['snakeladder-role-<code>']` is `'one'` (creator) or `'two'` (joiner), one `GET /:code` REST call for the immediate initial render, then the `snakeLadderSocket` connects and every `gameState` broadcast replaces local state directly. Rolling (`handleRoll`) just emits `rollDice { code, role }` and waits for the broadcast — the die is always server-generated, the client never sends or sees a roll value it invented. `ShareButtons` at `waiting`/`finished`, a "🔁 Rematch" button once finished (same `rematch` socket event and starter-alternation fix as Connect Four/Tic-Tac-Toe).
- **`api.js`** gained `createSnakeLadderGame`, `fetchSnakeLadderGame`, `joinSnakeLadderGame`, `getSnakeLadderShareUrl` — REST-only, mirroring the Connect Four equivalents; no move/roll REST call since that only ever happens over the socket.

## Chess — single-player and live 2-player

Added 2026-08-13, requested 2026-08-11 — the biggest game on the site: full legal-move generation (check/checkmate/stalemate, castling, en passant, promotion) is real chess-engine work, not something worth hand-rolling the way Connect Four's "4 in a row" check was. `chess.js` (MIT-licensed, the standard well-tested JS rules engine) is a new dependency and the sole authority on legality/game-over detection on both the single-player board and the live multiplayer one — nothing here re-implements chess rules by hand.

- **`src/games/chessAI.js`** — the "house" opponent, since chess.js is a rules engine, not an AI. Alpha-beta minimax (depth 2, or 3 once ≤10 legal moves remain — the endgame benefits most from the extra precision and has a much smaller tree by then) over `chess.js`'s legal moves, evaluating non-terminal leaf positions with material values plus standard piece-square tables (nudging knights/bishops toward the center, pawns toward advancing, the king toward safety behind its own pawns) and a small mobility term. A checkmate is scored directly (chess.js ends the game before material actually changes, so the material+PST eval alone wouldn't otherwise notice it) — a `depth` bonus rewards finding the fastest mate. Legal moves are shuffled before the top-level search so ties between equally-good moves don't always resolve the same way, same "doesn't feel robotic" goal as Connect Four's AI delay.
- **`src/games/ChessBoard.jsx`** — a shared presentational board used by *both* `Chess.jsx` and `ChessMultiplayer.jsx`, the one deliberate exception to this codebase's usual per-game board duplication (Tic-Tac-Toe/Connect Four/Snake and Ladder each duplicate their much simpler boards between single- and multiplayer). An 8x8 board with square selection, legal-move dots, a last-move highlight, a red check-glow on the king, and an `orientation` prop that flips which side renders at the bottom (the live game's second player sees their own pieces on the bottom, not White's) was judged too much shared complexity to safely write twice. Pieces render as Unicode chess glyphs (white/black pieces use genuinely different codepoints, e.g. ♔ vs ♚) with a CSS `text-shadow` outline so they stay legible on both light and dark squares in both light and dark theme — verified directly via computed styles, not just eyeballed.
- **`Chess.jsx`** (single-player) — human is always white and moves first, AI is black, same `onGameEnd`/`onReset` contract as every other game. Click-to-select-then-click-to-move (tap a piece, tap a highlighted destination), a small promotion picker modal (Queen/Rook/Bishop/Knight) appears when a pending move is a promotion-eligible pawn push, and a compact "Moves" list (from chess.js's `history()`) shows the running SAN move list below the board — a small extra touch this game's complexity earns that none of the simpler games need.
- **`ChessMultiplayer.jsx`** (`/games/chess/:code`) — same structural pattern as `ConnectFourMultiplayer.jsx`: `localStorage['chess-role-<code>']` is `'white'` (creator) or `'black'` (joiner), one `GET /:code` REST call for the immediate initial render, then the `chessSocket` connects, emits `joinRoom`, and every `gameState` broadcast replaces local state directly. Moving emits `makeMove { code, role, from, to, promotion }` and waits for the broadcast rather than updating optimistically, since the server is the actual legality authority. `ChessBoard`'s `orientation` is set from the viewer's own role, so both players see their own pieces at the bottom regardless of who created the match.
- **`api.js`** gained `createChessGame`, `fetchChessGame`, `joinChessGame`, `getChessShareUrl` — REST-only, mirroring the Connect Four equivalents; no move REST call since moves only ever go over the socket.
- Verified end-to-end in the browser: single-player legal-move dots match chess.js's own legal-move list exactly, the AI responds within about a second, promotion works; two real browser tabs playing live against each other confirmed the join broadcast, a synced move (with the turn correctly flipping) landing on the opponent's tab in under a second, and the board fitting without any horizontal overflow at a 375px mobile width.

## Ludo — live 2-4 player

Added 2026-08-17, the biggest step up in game architecture so far: every prior live game hardcodes exactly 2 roles, but Ludo needed a genuine N-player (2-4) pattern built from scratch, plus two capabilities no other game here has — a real pre-game lobby and a two-phase (roll, then pick a token) turn. No single-player mode.

- **`src/utils/ludoBoard.js`** — the board-*rendering* half of the backend's `utils/ludo.js` (duplicated by hand for the same reason Snake and Ladder's board util is — this copy only ever draws the board, it never runs game logic). Ludo's board isn't a uniform grid like every other game's, it's a "+"-shaped path inside a 15x15 bounding box, so this computes real layout data once at module load: a `LAYOUT[row][col]` classification (yard/home-stretch/center/ring/blank) for every cell, plus the ordered 52-cell shared ring. The ring's order is generated by an actual boundary walk (start at the cell beside red's yard, keep stepping to an unvisited ring-neighbor) rather than hand-listed coordinates — a first attempt at listing all 52 by hand kept landing on 56 cells instead (a small extra notch near one yard corner, structurally impossible to trim symmetrically without leaving dead-end cells), so the walk just stops once it has exactly 52 and a runtime check confirms indices 13/26/39 land next to green/yellow/blue's yards before the module is used anywhere — if that check ever fails, the whole page throws immediately rather than silently rendering a broken board.
- **`src/games/LudoBoard.jsx`** — a shared presentational board (only one exists, no single-player variant to duplicate against). Renders all 225 cells from `LAYOUT`, colors yard quadrants and home stretches per player, marks the 8 safe squares with a small star, and draws each player's 4 tokens at their current cell (`tokenCoords()`, yard/home-stretch/ring-square lookup). A token becomes a tappable, bounce-animated button exactly when it's in the current turn's `movableTokenIndices` — the parent page only ever passes that highlight down for the *viewer's own* turn, so other players' clients never render another player's tokens as tappable even though the server sends the same `movableTokenIndices` to everyone.
- **`src/games/PlayerChip.jsx`** gained `green`/`yellow` to its `RING`/`BG` color maps (additive — doesn't touch Snake and Ladder's existing `red`/`blue`/`orange` usage) and a `subtitle` prop overriding its default "Square {position}" text, since Ludo has 4 tokens per player rather than one board position — Ludo passes `"{n}/4 home"`.
- **`LudoMultiplayer.jsx`** (`/games/ludo/:code`, still the only *page* — no separate single-player component exists, see "Play vs House" below for how vs-AI reuses this same page) — `localStorage['ludo-role-<code>']` holds one of `red`/`green`/`yellow`/`blue`, set from the *server's* response on join (`joinLudoGame` returns `{ role }`, since unlike a 2-player game's join, the frontend can't predict which of 4 colors a joiner gets). Three render states: **lobby** (`status === 'waiting'`) shows each joined player, an invite `ShareButtons` block, and — creator-only, only once `players.length >= 2` — a "▶️ Start match" button that emits `startMatch`; a friend without a saved role sees the join form (name only, no color picker) until the match fills up. **In progress** shows a turn banner, `LudoBoard`, `DiceDisplay`, and a "🎲 Roll the dice" button enabled only on the viewer's own turn while `pendingRoll` is null — once a roll lands with legal moves, the button disables and the board's own highlighted tokens become the tap target (`moveToken`), no separate "confirm move" step. **Finished** shows a winner banner, Rematch, `ShareButtons`.
- **`Game.jsx`** — Ludo's default view (not arriving via `?mode=friend`) is a single "🏠 Play vs House" button, no name field — matching every other game's zero-friction single-player entry point even though under the hood it still creates a real `LudoGame` (see "Play vs House" below). A secondary "🆚 Challenge friends to a real match instead" link reveals the name + 2/3/4 max-players form (defaults to 2) for a genuine multiplayer invite, feeding `createLudoGame(name, maxPlayers)`.
- **`registry.js`** — Ludo's entry is `players: ['single', 'friend', 'multiplayer']`, so the homepage's "Single Player"/"2 Player"/"Multiplayer" filter chips all correctly list it — "Single Player" here launches vs-House the same one-click way as Tic-Tac-Toe/Connect Four, even though it's technically a real (auto-started) `LudoGame` match rather than a self-contained client-only game the way every other single-player entry is. "Multiplayer" (2026-08-20, requested directly) is a third `GAME_CATEGORIES` filter chip in `Home.jsx`, added alongside "Single Player"/"2 Player" specifically because Ludo is the site's first game with a real 3-4-live-player mode and there was no way to browse straight to it — `GameCard.jsx`'s `to` link treats `filterMode === 'multiplayer'` the same as `'friend'` (both open `?mode=friend`, i.e. Ludo's own challenge form, where the existing 2/3/4 "Max players" selector actually picks the count) rather than needing a separate route. Currently Ludo-only; any future game gets the same tab automatically just by adding `'multiplayer'` to its own `players` array.
- **`api.js`** gained `createLudoGame` (now `(name, maxPlayers, vsHouse)`), `fetchLudoGame`, `joinLudoGame`, `getLudoShareUrl`; **`socket.js`** gained a `ludoSocket` singleton for the `/ludo` namespace, same `autoConnect: false` pattern as every other game's socket.
- **`LudoBoard.jsx`'s yard colors** were bumped from a pale `bg-*-200/70` to a solid `bg-*-300` (matching the home-stretch stripes' own saturation) after a real phone screenshot showed green/blue/yellow's yards reading as gray/purple/orange — the colors were technically distinct (confirmed via computed styles in both themes) but too washed-out to tell apart at a glance, which defeats the point of a color-coded board.
- **`LudoBoard.jsx`'s yard shape** was reworked the same day, also from a screenshot: every one of a yard's 36 cells had its own thin grid border, same as the ring/home-stretch cells, making each corner look like a busy checkerboard instead of one solid block — the wrong shape for a real Ludo yard, which is a single colored square with one clean light inner panel holding the 4 starting tokens. `isYardTray(row, col, color)` (using `YARD_BOUNDS`, now exported from `utils/ludoBoard.js`) picks out that inner 4x4 region; yard cells render with **no per-cell border at all** (only ring/home/center cells keep the grid line), and the tray region gets a `bg-white/90 dark:bg-gray-900/70` fill distinct from the surrounding `YARD_BG` color — since adjacent same-styled cells with no border between them merge visually into one seamless area, this reads as "one colored square, one white panel" instead of a grid, with no change to the underlying cell classification or token math.
- **2-player color pairing**: for a 2-player match (including vs-House), the two seats are now `red` and `yellow` — diagonally opposite corners, matching how a real 2-handed Ludo game is actually seated — instead of the previous strict join-order assignment, which put them adjacent (`red`/`green`). This is entirely a backend change (`colorSequenceFor()` in `ludoController.js`, see `BACKEND.md`); the frontend already read every player's role dynamically (`game.players[1]?.role` for the house, `PlayerChip`'s color from each player's own `role`), so no frontend code needed to change for the new colors to show up correctly.
- **Color-to-corner layout corrected against a reference screenshot** (same day): the standard layout is red top-left, **blue top-right**, yellow bottom-right, **green bottom-left** — the first build had green/blue swapped. `utils/ludoBoard.js`'s `YARD_BOUNDS`, `homeStretchInfo`/`homeStretchCoords`, and `PATH_OFFSET` all got green and blue's entries swapped together (each color's home-stretch arm and ring-entry point are geometrically tied to its yard's corner, so all three had to move as one unit), plus `buildRingOrder`'s self-check assertions were updated to match (`blue` now expected near ring index 13, `green` near 39) — since this board has no test suite, that runtime assertion is what actually caught whether the swap was internally consistent, not just visual inspection. Re-verified the same way the original geometry was: `tokenCoords('blue', 0, 0)` now resolves next to the top-right yard, `tokenCoords('green', 0, 0)` next to the bottom-left one. **`LudoBoard.jsx`'s tray** also gained rounded corners (`trayCornerClass()`, rounding only the 4 outer tray cells so the borderless contiguous block reads as one rounded panel) and bigger tokens specifically while still in the yard (`w-5 h-5` vs. the path's `w-[15px] h-[15px]`), both matching the reference's cleaner look.
- **Center pinwheel and home-stretch saturation** (same day, "no compromise" follow-up after the corner-swap still didn't fully match the reference): the center square was a diagonal `bg-gradient-to-br` blur, not the reference's true 4-triangle pinwheel (each color's triangle meeting the others at a point, oriented toward that color's own approach direction — top=blue, right=yellow, bottom=green, left=red), and the home-stretch arms used a pale `bg-*-300` instead of the same bold `-500` as the yards/tokens. Fixed by (1) bumping `HOME_BG` to the exact same values as `TOKEN_BG` (`bg-red-500` etc, no dark-mode variant — the reference's colors don't change by theme, so neither does this now), and (2) replacing the gradient cell with a separate absolutely-positioned `conic-gradient` overlay spanning the whole 3x3 center block (a single grid cell's flat background can't render 4 diagonal wedges, but a conic-gradient with four 90°-wide stops centered on N/E/S/W can draw the pinwheel exactly) — `from -45deg` as the starting angle plus the right color order gets each triangle's centerline pointed the right direction. ## Fixed: a broken streak kept showing its old count until the next play

Reported directly (2026-08-17): missing a day showed the *previous* streak count (e.g. "Day 6") right up until the next attempt, which then jumped straight to "Day 1" — expected behavior is for the count to already read as broken/0 the day after a miss, so a fresh attempt correctly earns "Day 1," not a confusing double-reset. Root cause: `recordStreak()` in `dailyQuiz.js` only recalculates the count *when a completion is recorded* — every screen that just *displays* the streak (`DailyQuizBanner.jsx`, `PuzzleOfTheDayBanner.jsx`, `Account.jsx`, badge/points checks in `badges.js`/`levels.js`) reads the raw stored `{count, lastDate}` directly, so a broken streak's stale count sat there unnoticed until the next play overwrote it. Fixed by decaying it on every read instead: `readStreak()` now runs the stored value through `decayIfBroken()`, which zeroes `count` (keeping `lastDate` for reference) unless `lastDate` is today or yesterday — a single change under `getQuizStreak()`/`getPuzzleStreak()` that every caller already goes through, so no other file needed touching. There's no separate "resets every 7 days" mechanic — the count climbs indefinitely as long as no day is missed; "7-Day Streak" is only a badge *threshold* at 7, not a cycle. Verified locally: seeded a puzzle streak 3 days stale via localStorage, confirmed `PuzzleOfTheDayBanner`'s "Day N" badge correctly disappeared (0, hidden) on load rather than showing the stale number, while a same-day-completed Quiz streak still showed "Day 1" correctly.

## End-user accounts

Fully optional accounts — no email or phone number collected, and nothing on the site is gated behind login. `UserAuthContext.jsx` (separate from the admin panel's `AuthContext.jsx`, its own `userSession` localStorage key) provides `session`/`signup`/`login`/`logout`/`updateSession` and wraps the whole public site in `App.jsx`.

**Session refresh on load (2026-08-07):** the cached session (displayName/avatar) was only ever written at login/signup or by an explicit `updateSession()` call on that specific device — a profile change made on one device never reached an already-open session on another. Found directly: an account logged into both a phone and a desktop browser showed two different avatars, since only the device the change was made on had the new value (`fetchCurrentUser()` existed in `userApi.js` but was never actually called anywhere). Fixed with a one-time `useEffect` in `UserAuthProvider` that refetches `GET /api/users/me` on mount whenever a cached session exists, syncing this device's copy with whatever the account actually looks like server-side right now — no fresh login required. A failed refresh (e.g. offline, expired token) is silently ignored, keeping the stale cache rather than logging the visitor out.

**Cross-device stats sync (2026-08-07):** the same owner then reported the daily streak count and badge progress *also* differing between a phone and a desktop logged into the same account — expected, since both the streak (`dailyQuiz.js`) and badges (`badges.js`) were entirely `localStorage`-based with no account tie-in at all (this gap was already tracked in `PENDING_TASKS.md`). Built out now that a real account exists to attach it to: `EndUser` gained a `stats: Mixed` field (backend, mirrors the frontend's localStorage shape exactly — see `BACKEND.md`), and a new `frontend/src/utils/statsSync.js` bridges the two directions:
- **Push** — `pushLocalStatsToServer()` reads the current `dailyQuizStreak`/`dailyPuzzleStreak`/`twegleStats`/`twegleBadgesSeen` localStorage keys and `PUT`s them to `/api/users/me/stats` (fire-and-forget, no-op if logged out). Wired into the funnel points every mutation already passes through — `dailyQuiz.js`'s `recordQuizStreakCompletion`/`recordPuzzleStreakCompletion` and `badges.js`'s internal `update()` — so no call site elsewhere in the app (`Result.jsx`, `Game.jsx`, `TileReactions.jsx`, etc.) needed to change.
- **Pull + merge** — `syncStatsOnLogin(token)` runs once whenever `UserAuthProvider` has a session (on load, and right after login/signup), `GET`s the server's copy, and merges it with whatever's already in this browser's `localStorage` rather than blindly overwriting either side: each streak (Quiz and Puzzle, merged independently) takes whichever entry has the more recent `lastDate` (the one that actually kept that particular streak alive most recently); every other stat is a monotonic counter or a set, so merging is just "take the higher number" / "union the arrays" per field — no progress from either device is ever lost by logging in on a new one. An account synced before the 2026-08-09 streak split only has the old singular `streak` field server-side — read as that account's Quiz streak so nobody's existing progress is dropped; the Puzzle streak simply starts fresh. The merged result is written back to `localStorage` (so every existing read in `dailyQuiz.js`/`badges.js` picks it up with zero changes there) and pushed back up immediately, so both devices normalize to the same numbers right away rather than waiting for the next local mutation.
- `Badges.jsx`'s copy is now conditional on `session` — "Synced to your account — same progress on every device you log into" when logged in, the original "Tracked only in this browser" wording otherwise.

**Sync only ran once per page load (2026-08-07, same-day follow-up):** reported directly — revealing a puzzle on mobile made its "already attempted" tick show up correctly on mobile, but an already-open desktop tab logged into the same account never picked it up, even after refreshing the Puzzles tab (only a full page reload fixed it). Two separate causes, both fixed:
1. `syncStatsOnLogin` only ran inside a `useEffect` with `[]` deps in `UserAuthProvider` — since that provider wraps the whole app and doesn't remount on client-side tab/page navigation, it fired exactly once per full load and never again, so a change made on another device after that point was invisible until the next hard reload. Fixed by also re-running `syncStatsOnLogin` on every `visibilitychange` to `'visible'` (`UserAuthContext.jsx`) — the moment a visitor switches back to the tab is the most likely point they'd actually check something, without needing to poll continuously while the tab stays active. The effect's dependency array is now `[session?.token]` instead of `[]` so it re-attaches correctly if the session itself changes.
2. Even with a fresh sync running in the background, `hasCompletedQuiz`/`hasRevealedPuzzle` (`badges.js`) read `localStorage` directly at render time with no React state behind them — a background write from a completed sync doesn't by itself force an already-mounted `QuizCard`/`PuzzleCard` to re-render. Fixed by having `syncStatsOnLogin` dispatch a `'twegle-stats-synced'` `CustomEvent` once it's written merged data back to `localStorage` (`statsSync.js`) — the same pattern `badges.js` already used for its unlock-toast event — with `Home.jsx` listening and bumping a dummy `useState` counter to force a re-render of the grid. Verified locally by pushing a puzzle-reveal directly to a test account's server-side stats (simulating a second device) and confirming an already-open, non-navigated tab picked up the checkmark automatically after a simulated tab-focus event.

**Follow-up, same day — `visibilitychange` alone wasn't enough:** reported directly — switching in-app between the Games and Quizzes/Puzzles homepage tabs (not switching browser tabs or apps) never picked up a change made on another device, only a full page reload did. Root cause: `visibilitychange` only fires when the tab itself is hidden/shown (minimized, switched away from, backgrounded) — clicking between homepage tabs is plain in-page navigation, the document never becomes hidden, so the event never fires there at all. A reload "worked" only because a reload always re-syncs on mount regardless of any event. Fixed by adding a plain `setInterval(() => syncStatsOnLogin(session.token), 20000)` alongside the existing `visibilitychange` listener in `UserAuthContext.jsx` — re-syncs every 20 seconds while a session exists, independent of any visibility or navigation event, so switching between in-app tabs (or simply leaving the tab open and idle) converges within a few seconds either way, with no reload needed. Verified locally: cleared a fresh test account's state, switched to the Games tab (in-app, not a browser-tab switch), pushed a puzzle-reveal to that account directly via the API (simulating a second device), waited ~25s with zero visibility changes, then switched back to the Puzzles tab and confirmed the checkmark had appeared on its own.

Also fixed while investigating (at the time): `PuzzleOfTheDayBanner.jsx`'s eyebrow text was still "🔥 Puzzle of the Day" while `DailyQuizBanner.jsx`'s said "🔥 Daily Streak" — two different labels for what was, at the time, the same shared mechanic. Both were unified to "🔥 Daily Streak" — since reworded again to "🔥 Quiz Streak"/"🔥 Puzzle Streak" once the streaks themselves were split apart (see "Two independent streaks" above), so each banner's label now matches the actual independent number it shows.

- **Signup** (`Signup.jsx`) — username, password, and a Gamer Tag (the public display name, separate from the private username). ### Achievement levels + global leaderboard

Requested directly: a 10-level progression ("Achievements") that becomes the headline gamification feature, with the existing 7 one-off badges kept as a smaller, clearly separate "🎁 Bonus Badges" section — not replaced or merged into the same points. `frontend/src/utils/levels.js` exports `LEVELS` (10 entries: emoji, name, subtitle, points threshold) and `calculatePoints(stats, streakCount)`/`getLevelInfo(points)` — a byte-for-byte duplicate of `backend/src/utils/levels.js`, which the global leaderboard needs to compute everyone's points server-side (see BACKEND.md). Points are one combined score from everything already tracked (quizzes completed, puzzles solved, games played, shares, reactions, streak weeks) — no level name references a single activity type, since a mismatch there (an earlier draft had "Quiz Curious" as a name) was flagged directly as confusing.

`badges.js`'s single `update()` funnel point (every stat-mutating action already passes through it) now also runs `checkLevelUp()`: compares the current level against the highest one already toast-notified (`twegleLevelSeen` in localStorage, a separate key from the existing badge-seen tracking), and fires one `'twegle-level-up'` event if it's higher — "one," not one-per-level, so jumping several levels at once (e.g. the first stats sync after being away a while) shows a single toast, not a pile of them. Also hooked into `checkStreakBadges()` (called after a streak update, which doesn't go through `update()`), since streak weeks count toward points too.

`BadgeToast.jsx` now listens for `'twegle-badge-unlocked'`, `'twegle-level-up'`, and `'twegle-streak-reminder'` (added 2026-08-17) in one shared queue, but only a level-up toast gets a "📸 Share this" button (reusing `shareOrDownloadImage`, the same Canvas pipeline quiz/post results already use) — a level-up is the moment worth bragging about, a bonus badge is a smaller side accomplishment, and a streak reminder gets its own "▶️ Play now" link home instead.

**Streak-reminder toast** (2026-08-17, requested directly as "like when a user achieves a badge/completes a level on toaster/notification") — scoped as this same in-app toast rather than a real push notification, since push needs browser infrastructure (service worker subscriptions, a backend trigger) this site doesn't have yet. `dailyQuiz.js` gained `isStreakAtRisk(streak)`: true when the streak is real (`count >= 2`) and was last extended *yesterday* — meaning today is the last chance before it silently resets to 0 tomorrow; once today's already played (`lastDate === today`), it's no longer at risk. `badges.js`'s new `checkStreakReminders()` checks both the quiz and puzzle streaks independently and dispatches a `'twegle-streak-reminder'` event per at-risk one, gated by a `twegleStreakReminderShown` localStorage flag storing today's date — so however many times the site is opened in one day, the check still runs (cheap, local-only) but only the *first* at-risk result actually shows a toast. Triggered from `App.jsx`'s `PublicSite` via a mount-only `useEffect` — there was no existing "check on app load" pattern before this (every other toast fires only in direct reaction to a stat-mutating action), so this is the first one. `Badges.jsx` (page title changed to "🏆 My Achievements") leads with the level ladder: a highlighted "Your Level" card (current level, points, points-to-next, its own Share button) above a grid of all 10 levels shown locked/unlocked exactly like badges already were, then the original 7 badges below under the "🎁 Bonus Badges" heading, unchanged. A new `GET /api/leaderboard/levels` (public) backs a new `/leaderboard` page — top 100 accounts by points, computed server-side so nobody can fake a client-submitted score, linked from Badges, the footer, and the header's 🏆 icon (retitled "My Achievements" to match). Requires an account to appear on it, same reasoning as the existing per-game leaderboards — a guest's progress only exists in their own browser, so there's no identity to globally rank.

Verified in the browser: seeded a real jump in points (10 fake quizzes' worth) then triggered one real tracked action (a post reaction) to confirm `checkLevelUp()` fires from the real `update()` funnel, not just in isolation — confirmed `twegleLevelSeen` updated to the correct new index, the Badges page immediately showed the new level and newly-unlocked level cards, the Share button completed with no console errors, and the leaderboard page correctly listed a real synced test account ranked by its server-computed points. Confirmed dark mode text is legible on both new pages.

**Points rebalance (feedback-driven, right after shipping):** the owner flagged two problems with the first version — the top level was reachable in one sitting, and it was never clear which activity earns how many points. Games and reactions are a single click each and infinitely repeatable (unlike quizzes/puzzles, which are naturally capped by how much content exists), so the original uncapped formula let someone grind one game hundreds of times and skip straight to the top level. Fixed in `levels.js`: `calculatePoints()` now runs `Math.min()` caps before summing — only the first `MAX_COUNTED_PLAYS_PER_GAME` (10) plays of each game slug count, and only the first `MAX_COUNTED_REACTIONS` (50) total reactions count. Quizzes, puzzles, and shares stay uncapped (shares deliberately so — sharing is the one behavior worth rewarding without limit). Per-action point values and the 10 level thresholds were raised alongside the caps so reaching the top still takes sustained, varied activity rather than one binge. `Badges.jsx` also gained a "💡 How to earn points" table — a plain list of every scoring action, its point value, and its cap (if any), pulled directly from `levels.js`'s exported constants so it can never drift out of sync with the real formula.

## Share before attempting

Every share button on the site used to be tied to *after* finishing something — a quiz result, a friendship-quiz score, a game outcome, or opening a post. There was no way to invite a friend to anything before either of you had opened it. Built once as a shared component, then wired into **every** content tile: `QuizCard.jsx`, `GameCard.jsx`, `PostCard.jsx` (jokes/funny lines/quotes/motivational quotes/memes), `StoryCard.jsx`, and `FriendshipQuizCard.jsx` all show the same small 🔗 icon in the card's corner.

- **`TileShareButton.jsx`** (new shared component, `frontend/src/components/`) — takes `{ title, shareUrl, shareText }` and renders the icon plus a floating popover (Share/WhatsApp/Copy link). Every card passes its own item-specific `shareUrl`/`shareText`, so sharing any tile always previews *that specific* quiz/game/joke/meme/friendship quiz, never a generic site-wide link. Each card's `shareUrl` points at a crawler-friendly backend `/api/share/*` route (see `BACKEND.md`) built from that item's own title/description:
  - Quiz → `getQuizIntroShareUrl(slug)` → `GET /api/share/quiz/:slug`
  - Game → `getGameShareUrl(slug)` → `GET /api/share/game/:slug` (new — games have no database row, so the backend keeps a small `GAME_META` map mirroring `games/registry.js`, same duplication pattern as `GAME_SLUGS` already used for play-tracking)
  - Post (joke/funny line/quote/motivational quote) → `getPostShareUrl(post._id)` → `GET /api/share/post/:id` — this route already existed (built for the individual `/post/:id` page's own share buttons) and needed no changes; the tile just reuses it
  - Friendship Quiz → `getFriendshipQuizIntroShareUrl(slug)` → `GET /api/share/friendship-quiz/:slug` (new — shares the *template* before anyone's filled it in, distinct from the existing instance/result share routes)
  - Story → `getStoryShareUrl(slug)` → `GET /api/share/story/:slug`
- **The popover is `absolute`, not part of the card's normal flex flow.** A first version (built for `QuizCard.jsx` only, before this was generalized) rendered it as a plain block between the description and the action pill, which pushed that pill down and made one card visibly taller than its row-mates whenever its popover was open — breaking the equal-card-height invariant documented under "Known decisions" below. Floating it above the content instead (`position: absolute`, anchored to the icon) fixes this: opening/closing the popover never changes the card's own height.
- **The popover's buttons are plain `<button>`s, not `<a>` tags**, even for WhatsApp (which normally is a real link elsewhere in the app, e.g. `ShareButtons.jsx`). Every one of these cards is itself a real `<Link>` (so ctrl-click/right-click "open in new tab" and crawlers still work) — nesting an `<a>` inside another `<a>` is invalid HTML and breaks click behavior, so the WhatsApp button instead does `window.open(waUrl, '_blank', 'noopener,noreferrer')` from a plain button. Every handler also calls both `preventDefault` and `stopPropagation`, since the popover sits inside the card's own `<Link>` and a click needs to reach the button without also navigating into the item underneath it. Closes automatically on an outside click (a `mousedown` listener attached only while open).

## Back navigation

Every content detail page (Quiz, Result, PostView, StoryView, HoroscopeView, Game, TicTacToeMultiplayer, FriendshipSetup/Play/Result, CompareInvite/Result) now shows a "← Back" control at the top, via a new shared `BackButton.jsx` component — requested directly, since previously only some pages had any "back to home" link at all, and only at the bottom of the page.

- **Uses browser history (`navigate(-1)`), not a fixed link to `/`.** This is the key design choice: since the homepage's active tab/filter lives in the URL (`?tab=stories`), going back via actual history returns to the *exact* prior URL — tab and filter included — rather than resetting to a blank `/` (which the homepage always renders as the Quizzes tab). This directly fixes a reported bug: clicking a story from the Stories tab, then clicking Back, used to always land back on Quizzes; now Stories stays selected.
- **Falls back to a plain `<Link to="/">`** when there's no real browser history to go back to — `location.key === 'default'` is React Router's own signal that this is the first entry in the session's history, which happens when a visitor opens a content page directly (a shared link, a bookmark) rather than navigating from within the app. Without this fallback, `navigate(-1)` in that case would either do nothing or leave the app entirely (back to whatever page — if any — was open before Twegle in the browser tab's history).
- Deliberately doesn't touch the existing bottom-of-page links ("Take another quiz," "See more," "Back to Twegle") — those serve a different intent (browse more content, fresh start), so they still point at a plain `/`.

`Footer.jsx` now shows Instagram/Facebook/YouTube/LinkedIn icons next to the brand blurb (2026-08-01, requested once the actual accounts existed) — plain `<a target="_blank">` links to the handles actually registered: `instagram.com/twegle.official`, `youtube.com/@twegle`, `linkedin.com/company/twegle` (Instagram needed the `.official` suffix since the bare `twegle` handle was already taken there; the other two got the exact handle). ## "You might also like" suggestions

`Result.jsx`, `PostView.jsx`, and `StoryView.jsx` all end with 4 suggested-next cards (`QuizCard`/`PostCard`/`StoryCard`, same components used everywhere else, so they look identical to the homepage grid) instead of just a bare "take another quiz"/"see more" link — 4 rather than 3 so the 2-column grid (see below) fills evenly as a 2×2 block instead of leaving one card alone on its own row. **Bug fixed 2026-07-31: cards were badly cramped in this section.** All three of these pages are narrow single-column reading pages (`max-w-xl`, 576px), but the suggestion grid was `sm:grid-cols-3` — the same 3-column count used on the wide homepage grid (`max-w-6xl`, 1152px). Verified via computed `getBoundingClientRect()` measurements in the browser: story suggestion cards went from 332px tall (badge wrapped to 112px) down to 208px tall (badge a clean single-line 32px), same improvement confirmed on quiz and post suggestions; confirmed all three pages render exactly 4 suggestion cards after the count change.

## Merged Posts tab + homepage tab reorder (2026-08-05)

The post categories (Jokes/Funny Lines/Quotes/Motivational Quotes — Memes was a 5th category until 2026-08-06, see below) share one **"💬 Posts"** tab in `Home.jsx` — no backend/model change (`Post` already had one `category` field), purely a frontend consolidation. ## Ludo safe-square (star) positions were geometrically wrong for 3 of 4 colors

Reported directly with a very specific symptom: "star is wrong at every place, correct with one only which is just near to blue." Root cause, found by writing a small standalone script that imported `ringSquareCoords` and checked 4-fold rotational symmetry across all 52 ring indices: the board's `classifyCell` geometry (rows/cols 6-8 forming the "+"-shaped band) naturally produces **56** connected ring cells, not the 52 a real Ludo path has — the 4-cell excess is exactly the 4 diagonal corners of the center 3x3 block, `(6,6)`, `(6,8)`, `(8,6)`, `(8,8)`, the single cells where the horizontal and vertical arms structurally overlap (a real board has no separate square there — it's purely a connectivity waypoint where one arm turns 90°). The previous `buildRingOrder()` just walked the ring and **stopped once it collected 52 cells**, which chopped off whichever 4 cells happened to be left over at the very end of the walk — not these 4 specific corners. Since the walk always starts at blue's own square, that truncation left blue's region correct by construction while silently shifting red/green/yellow's start squares (and therefore every star square past blue, since they're all defined as fixed offsets from each color's start) off their true symmetric position. A verification script confirmed the bug precisely: rotating index `i`'s coordinates 90° should equal index `i+13`'s coordinates for a truly symmetric ring — the old order failed this check at literally every index past 0.

Fixed by walking through all 56 connected cells (for connectivity — the walk still needs to physically step through the 4 corner cells to turn from one arm into the next) but only **assigning a global index to the 52 that aren't one of those 4 corners** — the corners are visited but skipped from the numbered sequence. This is a purely geometric/rendering fix; `PATH_OFFSET`, `SAFE_SQUARES`, and every backend game-logic number were untouched (the 52-square, 13-per-arm abstract model was always correct — only the screen-coordinate mapping for each abstract index was wrong). Verified via a script re-checking the same rotational-symmetry property against the fixed code (0 mismatches across all 52 indices, versus dozens before) and confirming all 4 color starts (`ringSquareCoords(0/13/26/39)`) land exactly on their expected symmetric cell. Re-verified live in the browser: read every rendered star's on-screen position in a vs-House match and confirmed the 8 stars form 4 exact mirror-pairs (e.g. `(1,8)`/`(2,6)` near red, `(8,2)`/`(8,13)` near yellow-green, etc.) — no more visible asymmetry — with gameplay (roll, board render) unaffected.

## Fixed a real, major bug: rolling N sometimes visibly moved a token N+1 squares

Reported directly, described as "very major": "suppose 4 occurs, the pawn walks 5 times, it should only 4 — this happening lots of time." Root cause was the exact same 56-vs-52-cell geometry the star-position bug above already surfaced, but a deeper consequence of it that the earlier fix didn't catch: the previous `buildRingOrder()` walked all 56 physically-connected ring cells (needed for connectivity) but only assigned a *global index* to 52 of them, skipping the 4 diagonal corner cells `(6,6)`/`(6,8)`/`(8,6)`/`(8,8)` on the theory that they were "pure connectivity waypoints, not real squares." That assumption was wrong — a fresh adjacency check (comparing every consecutive ring index's on-screen distance) found exactly 4 points around the ring where consecutive indices are 2 physical cells apart instead of 1, precisely at those 4 skipped corners. A degree check on the full 56-cell graph confirmed why: every one of the 56 cells has exactly 2 ring-neighbors, forming one single unbroken loop with no dead ends — meaning those 4 corners are genuine, physically distinct board squares (a real Ludo board really does have a square at the point where each arm turns 90°), not shortcuts. Skipping them from the index was itself the bug: the token's *stored* local-position count stayed perfectly correct (a roll of 4 always added exactly 4 to the number), but the *rendered* board silently jumped over 2 physical squares in one index step whenever a move happened to cross one of these 4 points — which is exactly "the dice said 4, the pawn visibly walked 5."

The real fix: stop trying to force the count down to the traditional 52 and index all 56 walked cells with no exclusions, so every single index-to-index step is physically adjacent by construction — the only way to rule this class of bug out entirely, rather than patching around it. This changes the board's local-position numbering everywhere it's duplicated: `PATH_OFFSET` is now `{blue:0, red:14, green:28, yellow:42}` (14 apart on a 56-loop, not 13 on 52), `SAFE_SQUARES` renumbered to the same 8 physical star squares as before (`[0,9,14,23,28,37,42,51]`), and each color's home-stretch entry point moved from local 51 to local 55 (`HOME_ENTRY`), finish from local 57 to local 61 (`FINISHED`) — both backend (`utils/ludo.js`) and every frontend duplicate (`utils/ludoBoard.js`, `games/ludoHouseAI.js`, the two `=== 57`/`>= 51` finish/threshold checks in `LudoBoard.jsx` and `LudoMultiplayer.jsx`) updated together so the numbering stays consistent end-to-end. `legalMoves`/`applyMove` in `utils/ludo.js` needed no logic changes — they're already written generically against the constants.

Verified two ways before touching any live code: (1) an exhaustive offline script confirmed every one of the 56 corrected ring transitions is physically adjacent (0 mismatches, versus 4 real 2-cell jumps before the fix) and that all 4 colors still start next to their own yard at the new 14-apart offsets; (2) a full simulation of every possible roll (1-6) from every possible starting local position (0-54) for every color confirmed the number of physical squares crossed now exactly equals the roll — 0 mismatches across the complete space, versus a real, reproducible defect before. Re-verified live: played a vs-House match, confirmed a token correctly left the yard on a 6 and then advanced by exactly its next two rolls (5, then 4) with no console errors, module load succeeding without tripping the ring's own runtime geometry assertion (now checking for 56 cells and the 14/28/42 color-start offsets).

## Fixed: 3-/4-player Ludo matches couldn't start (creator's own role was hardcoded wrong)

Reported directly (2026-08-18): a 3-player match where both invited friends joined successfully still showed no way to start it — the "▶️ Start match" button, which is only ever shown to the creator, simply never appeared. Confirmed with 2-player matches, working fine.

Root cause: `Game.jsx`'s Ludo challenge-form handler hardcoded `localStorage.setItem(\`ludo-role-\${data.code}\`, 'red')` for the creator, copying the exact pattern every *other* live game already uses (Connect Four/Snake and Ladder/Chess/Tic-Tac-Toe all really do assign a fixed first role regardless of player count). Ludo is the one game where that assumption breaks: `ludoController.js`'s `colorSequenceFor(maxPlayers)` only returns `['red', 'yellow']` for a 2-player match — 3-/4-player matches use the standard clockwise `['blue', 'red', 'green', 'yellow']`, so the creator (`players[0]`) is actually **'blue'**, not 'red'. The hardcoded 'red' only ever matched by coincidence in the 2-player case, which is exactly why "it works fine with 2 player" but silently broke for 3/4: `isCreator = game.players[0]?.role === role` evaluated to `false` for the real host, hiding their own Start button, and had they somehow triggered it anyway, the server-side `game.players[0]?.role !== role` check in `ludoSocket.js` would have rejected it the same way.

Fixed by having the frontend store whatever role the *server* actually assigned instead of guessing: `createGame`'s response now includes `role` (matching the shape `joinGame`'s response already returns for everyone who joins after the creator — see `BACKEND.md`), and both of `Game.jsx`'s Ludo branches (`handleChallengeSubmit` and `handlePlayVsHouse`) store `data.role` instead of a literal `'red'`. vsHouse is unaffected functionally (always 2-player, so `data.role` resolves to `'red'` anyway) but now reads the real value consistently rather than a special-cased guess.

Verified locally via a real 3-player match across 3 browser tabs (localStorage cleared per tab, matching every prior live-game test in this project): confirmed the creator's stored role now reads `'blue'` (not `'red'`), confirmed both friends joined with `'red'`/`'green'`, confirmed the "▶️ Start match (3 joined)" button correctly rendered for the creator once both had joined, and confirmed clicking it actually flipped the match to `in_progress` with no errors. Also confirmed via a direct API check that a freshly created 4-player match's `role` in the create response matches `players[0].role` (`'blue'`) the same way.

## Ludo yard tokens truly centered per quadrant + no dark-mode color shift on yard corners

Two more direct corrections (2026-08-17) against the same reference image: (1) each yard's 4 starting tokens looked slightly off-center within their "part" of the tray, and (2) the 4 yard corner colors visibly muted/shifted in dark mode instead of staying the exact same blue/red/green/yellow.

A faint cross divider (two 1px lines) was added inside each tray so the 4 equal parts are actually visible, matching the reference. Path/home-stretch tokens are unaffected — those only ever need to center within a single cell, which plain grid placement already does correctly.

**Dark-mode yard colors**: `YARD_BG` previously had a `dark:bg-*-900/80` variant per color, which is exactly what was shifting blue/red/green/yellow to a darker, desaturated tone in dark mode. Removed those dark: overrides entirely (requested directly, "no change") — the yard corners now render the identical `bg-*-300` value in both themes, matching how `HOME_BG`/`TOKEN_BG` already had zero dark-mode variant.

## Fixed a real cross-account data leak: logging out didn't clear this browser's local stats

Found by direct questioning, not a bug report (2026-08-18) — the owner noticed Badges/My Achievements still showed real numbers right after logging out, and asked what would happen if a *different* account logged in next on the same browser. Root cause: `UserAuthContext.jsx`'s `logout()` only ever removed the session token — the actual stats (`twegleStats`, streak keys, the weekly-recap daily-activity log) stayed in `localStorage`, so the browser kept looking like the just-logged-out account to every local read, and `statsSync.js`'s merge-on-login (which keeps whichever side of each stat is higher) could pull that leftover data into whichever account logged in next on a shared device.

Fixed by clearing local data on **logout**, not login — new `clearLocalStats()` (`badges.js`), `clearLocalStreaks()` (`dailyQuiz.js`), and `clearDailyActivity()` (`weeklyRecap.js`, added in a same-day follow-up after the first fix missed this third, separately-tracked key), all called from `logout()`. Deliberately *not* cleared on login — that would have discarded legitimate guest progress earned between logging out and logging back in. Clearing on logout means guest activity after that point starts from a clean 0 (nothing to leak) while still correctly merging into whichever account logs in next, same as before.

A related, deeper bug surfaced from continued testing the same day: "This Week / Your Twegle Wrapped" wasn't actually included in `statsSync.js`'s cross-device sync at all (points/badges/streaks were, this wasn't), so logging into the same account on a second device never showed the first device's weekly activity — fixed by adding it to the synced blob with a per-day, per-kind max-merge (`mergeDailyActivity()`, same "keep whichever side got further" approach the other merges already use). And the actual root cause of data going missing at all: every one of `badges.js`'s 5 action recorders called `recordDailyActivity()` **after** `update()`'s automatic push to the server, so that action's own daily tally was never included in the push that just happened — only the *next* action would pick it up, and logging out before doing anything else lost it the moment the new clear-on-logout fix ran. Fixed by reordering `recordDailyActivity()` to run before `update()` in all 5 recorders.

Verified locally: seeded 23 points on one test account, logged out, confirmed Badges immediately showed "Fresh Face, 0 points" with no reload; logged into a different account, confirmed no leak. Separately verified the sync fix with a real two-device simulation (seed activity on one simulated device, log in, confirm pushed to the server; clear local storage to simulate a genuinely fresh second device, log in again, confirm the first device's activity is pulled down correctly).

## Draft preview link

Every admin list page (Quizzes/Posts/Stories/Puzzles/Friendship Quizzes) has a "👁 Preview" button on each row, sitting outside the existing `canWrite` gate so Analysts can use it too — previewing is a read action, not a write. Clicking it calls `GET /api/admin/preview-link` for a short-lived signed token, then opens the item's real public page in a new tab with `?preview=<token>` appended (`AdminPreviewButton.jsx`), rather than rendering some separate admin-only preview view — this means a draft renders through the exact same component a real visitor would see, so there's no risk of the preview looking different from what actually goes live.

Every public content page (`Quiz.jsx`, `Result.jsx`, `PostView.jsx`, `StoryView.jsx`, `PuzzleView.jsx`, `FriendshipSetup.jsx`) reads `?preview=` via `useSearchParams`, forwards it to its `fetch*By*` call in `api.js` (which appends it as a query param), and shows a small amber `PreviewBanner` ("👁 Preview mode — this is a draft, not live on the site") whenever it's present. `Quiz.jsx` also forwards the token into the URL when navigating to `Result.jsx` on finishing a quiz, since that page independently re-fetches the quiz and would otherwise 404 on a draft.

`BackButton.jsx` has a preview-specific case: on a page reached without any browser history (the normal state for a page just opened via `?preview=`), its usual fallback is a plain link to the homepage — but landing an admin on the live public homepage after "Back" reads as if the draft just vanished. Since the preview tab was opened by `window.open()` from the admin panel, it's allowed to close itself, so this case renders "✕ Close preview" instead, calling `window.close()` to return the admin straight to the panel tab they already had open. Every other page (reached via real in-tab navigation, e.g. from Quiz.jsx to Result.jsx after finishing a previewed quiz) still has real history and uses the normal back-navigation behavior.

Every real-visitor side effect these pages normally trigger — view/share engagement recording, quiz play-count recording, "already attempted" badge/streak tracking — is skipped whenever a preview token is present, so previewing a draft never touches real analytics or a real visitor's local stats. Friendship Quiz previewing is deliberately fetch-only: the actual "get my shareable link" submit flow that creates a real instance was left untouched, since that's a genuine content-creation action a preview shouldn't need to special-case.

Verified locally: created a draft quiz, confirmed a plain (no-token) request to its slug 404s, confirmed a garbage/tampered token still 404s, confirmed the real preview token returns the draft and renders it with the banner in the browser, played it through to Result.jsx and confirmed the banner and token carried over there too, and confirmed via a direct `PlaySession` count check before/after that finishing the previewed quiz recorded zero real plays.

## Known decisions worth knowing about

- `react-router-dom` has open security advisories in npm's audit database, but every one is about server-rendering / server-action features this app does not use (we're a plain client-side Vite app — only `BrowserRouter`, `Routes`, `Route`, `Link`, `Navigate`). Worth re-checking `npm audit` occasionally as new versions ship.
- **Quiz card colors must come from `src/gradients.js`, never free text.** Tailwind generates CSS by scanning literal class name strings in the source code at build time — it cannot see class names that only exist as data from the API/database at runtime. This caused a real bug (cards showing no color at all) once quiz data moved from a source file to the live database. The fix: a fixed palette lives in `gradients.js` as literal strings Tailwind can see, and the admin panel's "Card Color" dropdown only ever picks from that list — never accepts typed-in values. When adding new quiz topics needs more colors than are safelisted, add the new gradient string to this file first — see `BACKEND.md`'s bug #3 for the same lesson applied to the `language` field (new fields need backfilling on old data, new gradients need safelisting before use). Post category colors in `postStyles.js` reuse gradients already safelisted here, so no changes were needed there.
- **`ShareButtons` takes an optional `shareText` prop now**, instead of always deriving share copy as `` `${title} — take the quiz!` ``. Needed once the component started getting reused for friendship-quiz links and score reveals, where "take the quiz!" read oddly tacked onto "How well do you know Ashish?" or "I scored 6/8...". Passing `shareText` overrides the default; every other caller (quiz results, posts) is unaffected since the prop is optional.
- **`ShareButtons` also takes an optional `align` prop** (`'center'` default) — added 2026-08-09 so the footer's "Share Twegle" row could pass `align="start"` and sit flush left under its left-aligned label, without disturbing every other caller (Result/Post/Puzzle pages, etc.), which all still want the buttons centered under a centered card. The site-wide "Share Twegle" copy was also updated the same day to mention Puzzles and Games (`"Check out Twegle — free quizzes, puzzles, games, jokes, quotes & more, no sign up needed!"`), reported as stale text still only naming quizzes/jokes/quotes after both content types shipped — updated in both `Footer.jsx` and `ShareSidebar.jsx`.
- **The Clone feature's generated title needs a unique tag, not just a static `"(Copy)"`.** Found while testing Clone on a Hindi-titled quiz: the backend's slug generator only keeps Latin/numeric characters, so a Hindi title contributes nothing to the slug — only the English `"(Copy)"` suffix survived, meaning every clone of every Hindi quiz collided on the same slug (`copy`). Fixed on both sides: the clone title now includes a short random tag (`(Copy a1b2)`), and the backend's slug generator has its own fallback for titles that reduce to nothing at all — see `BACKEND.md`'s bug #5 for the full story.
- **`ShareButtons`'s "Copy link" handler must not let a failed clipboard write silently swallow the share-tracking call.** Found while testing post-share analytics: `navigator.clipboard.writeText()` can throw ("Write permission denied") in contexts without clipboard permission — notably in-app browsers like Instagram/TikTok's, which is exactly where this app's traffic is expected to come from. Since the original code did `await navigator.clipboard.writeText(url)` before firing the `onShare` callback, a denied clipboard permission meant the share was never counted at all, with no visible error. Fixed by wrapping the clipboard call in its own try/catch so `onShare?.()` always fires on click, regardless of whether the copy itself succeeded.
- **`QuizCard`/`FriendshipQuizCard` need `h-full flex flex-col` on the card itself, not just on the grid wrapper.** Found from a real report: card tiles in the same row were visibly different heights. `Home.jsx` wraps each card in a `<div>` that (correctly) stretches to fill its CSS Grid row, but the `<Link>` inside — the actual colored card — had no explicit height, so it only grew to fit its own content, leaving an unstyled gap below shorter cards while the wrapper silently stretched around it. Fixed by making the `Link` itself `h-full flex flex-col` with `mt-auto` on the bottom action row, so every card in a row now fills the same height and the "Take the quiz"/"Fill it in" pill lines up at the same vertical position regardless of how long the title/description is. The inline post cards (jokes/quotes/etc.) in `Home.jsx` didn't have this bug — they're the direct grid item with no extra wrapper, so CSS Grid's default `align-items: stretch` already sized them correctly.
- **Admin list pages must not debounce their very first load.** Found from a real report of the admin panel "flickering" when switching between Quizzes/Posts/etc. `QuizList.jsx` and `PostList.jsx` fire `load()` inside `setTimeout(load, 250)` so typing in the search box doesn't send a request per keystroke — but that same 250ms delay was also applied to the initial mount, meaning every single navigation to either page guaranteed at least 250ms of a bare "Loading..." state before the real content ever appeared, even though the request itself resolves in well under 50ms locally. Fixed with an `isFirstRender` ref: the first run of the effect calls `load()` immediately, and only subsequent filter/search changes get debounced.
- **The hero band's quiz/post counts are fetched, not hardcoded.** They used to be a literal `"24 quizzes"` / `"85+ jokes & quotes"` string in `Home.jsx`, manually edited (and easy to forget) every time new content shipped. Now a one-time `useEffect` fetches `GET /api/quizzes` and `GET /api/posts` with no language filter (both endpoints return every language when the param is omitted) and counts them client-side (non-meme posts only, matching the "jokes & quotes" wording), with the old hardcoded numbers kept only as a same-value fallback shown for the brief moment before the fetch resolves.
- **When rendering content that depends on which tab/filter is active, tag the fetched data with what it was fetched for — don't just clear-and-refetch and trust that timing works out.** `Home.jsx` used to call `setItems(null)` in a `useEffect` after `activeTab` changed, but React still renders once with the *new* `activeTab` and the *old* `items` before that effect runs. Switching from Quizzes to Jokes could momentarily render quiz objects through the post-card code path (which reads `post.category`, undefined on a quiz) — a full crash if a `.gradient` property gets read off that undefined lookup. Fixed by storing fetched results tagged with the tab/language that produced them (`{ tab, language, items }`) and only trusting `items` when that tag matches the current `activeTab`/`language` — otherwise it shows the loading state instead of stale data. Worth reusing this pattern anywhere content is fetched per-tab/per-filter.
- **A `transition-[width]` utility on a `position: sticky` flex item can leave the computed width visibly stuck at the old value after a class change, in this dev environment at least.** Found while building the collapsible admin sidebar: toggling between `lg:w-16`/`lg:w-56` updated the element's `className` correctly (confirmed via DevTools) and worked fine on a fresh page load, but a same-session React state toggle left `getComputedStyle(...).width` reporting the *previous* value indefinitely — not a transition timing issue (waited well past any reasonable duration). A plain test element with the same class, added fresh to the page, picked up the correct width immediately, meaning the utility itself wasn't broken — something about applying it to *this specific* sticky flex item was. Removed the transition entirely rather than chasing the exact cause further, since an instant width snap was an acceptable trade for a working toggle. Worth avoiding `transition-[width]` on sticky elements here until/unless this gets properly root-caused.
- **Bug fixed 2026-07-31, then reworked the same day: clicking a homepage filter visibly yanked the sticky sidebar out of place, not just scrolled the content.** First attempt clamped `Home.jsx`'s scroll-reset to never go past the results grid's top (`Math.min(currentScrollY, contentTop)`, via a `preScrollRef` captured synchronously in every filter's `onClick`, applied through `setTimeout(fn, 0)` rather than `requestAnimationFrame` since this environment's headless preview tab doesn't reliably fire rAF callbacks — confirmed separately via a failed screenshot and a timed-out rAF polling loop). That technically kept the sidebar's on-screen position unchanged for content-rich tabs, but landed at a *different* offset per tab depending on how much content that tab had (a content-sparse tab like Memes never let the sidebar get "stuck" in the first place) — reported back as still not fixed, since the inconsistency across tabs read as more confusing than a single predictable behavior. Reworked to a plain, unconditional `window.scrollTo(0, 0)` on every filter/tab change instead — every click now lands at the exact same place (hero, sidebar, and content all visible together from the top) regardless of which tab or how much content it has, trading "sidebar never visually moves" for "behavior is always identical and predictable," which is what was actually being asked for. The `preScrollRef`/`selectFilter`/`contentRef` machinery from the clamped attempt was removed entirely.
- **Newest is now the default sort, and listed first** (2026-08-01, requested directly) — `sortMode`'s initial state changed from `'trending'` to `'newest'`, and the two toggle buttons swapped order so Newest reads left-to-right first, next to the language switcher.
- **Sidebar spacing tightened** (2026-08-01, requested directly, "so space can be created for Menu items") — the EN/हिंदी and Trending/Newest toggle pills shrank (smaller padding and font size), and the vertical gaps between the language row, sort row, and tabs list in `Home.jsx`'s sidebar were all reduced, leaving more room for the tab list itself without changing anything structurally.
- **Trending/Newest sort toggle generalized to every homepage tab, not just Quizzes.** Previously the sort toggle only rendered (and only worked) on the Quizzes tab. Now every tab — Friendship Quiz, Memes, Games, Stories, Jokes, Quotes, Funny Lines, Motivational — shows the same toggle and sorts real data: quizzes/games sort "Trending" by `totalPlays`, friendship quizzes by `totalAttempts`, and everything else (posts, stories) by a new `totalEngagement` field (views+shares aggregated server-side from the existing `PostEngagement`/`Engagement` models, mirroring the aggregation already used for quiz play counts) as a popularity fallback since those content types have no "completion" concept. "Newest" sorts by `createdAt` for everything with a real creation date; Games (which are code, not database rows, so they have no `createdAt`) approximate it by reversing the static games registry, whose order roughly matches when each game actually shipped.
- **Trending/Newest moved next to the language switcher.** Requested directly: since Trending/Newest is a "global filter" like language (applies the same way regardless of which tab is active), it didn't make sense to bury it at the bottom of the sidebar, below the tab-specific category chips. Moved it to sit immediately after the EN/हिंदी toggle, before the tabs row — the sidebar now reads as "global filters first (language, sort), then content-type-specific filters (tabs, category chips)" instead of mixing the two.
- **Homepage tab order: Funny Lines now immediately follows Jokes**, ahead of Quotes and Motivational Quotes — grouping the two quick one-liner formats together. New order: Quizzes, Friendship Quiz, Memes, Games, Stories, Jokes, Funny Lines, Quotes, Motivational Quotes.

## PWA support (installable, offline-capable for viewed pages)

Not a native app — a plain web app that can be installed to a phone's home screen and keeps working (for content already viewed) without a connection, via `vite-plugin-pwa` (Workbox under the hood).

- **`vite.config.js`** — the `VitePWA()` plugin config. `registerType: 'autoUpdate'` means a new deployed version takes over silently, no user-facing "update available" prompt (kept simple for now). `devOptions: { enabled: true }` lets the service worker actually run under `npm run dev`, not just a production build — otherwise "does this work" could only ever be answered after a full build+preview cycle.
- **Update detection was silently broken for months (fixed 2026-08-07)**: `registerType: 'autoUpdate'` only controls how the *service worker itself* behaves once a newer one is found (`skipWaiting`/`clientsClaim`, baked in automatically) — it says nothing about how often the *browser* actually checks for a newer one. Browsers only check for service worker updates on a fresh navigation, and an SPA tab that's just left open across a deploy never triggers one. The app was relying entirely on `vite-plugin-pwa`'s auto-injected registration script (the default when `injectRegister` isn't set), which registers the worker exactly once and never checks again — so a visitor who kept a tab open (or even just didn't force-reload) across a new deploy could keep running stale JS indefinitely, with no error and no visible sign anything was wrong. This surfaced repeatedly as real features appearing to "not work" that were actually already fixed and deployed — confirmed multiple times by reproducing the exact same steps in a fresh browser session and having them work correctly, while the reporter's own tab kept showing the old behavior until manually unregistering the service worker in DevTools. Fixed by registering explicitly in `main.jsx` via `virtual:pwa-register` instead (`vite.config.js` sets `injectRegister: false` to avoid double-registering): checks for an update on every tab focus (`visibilitychange`) plus hourly as a baseline, and reloads the page exactly once as soon as a new worker takes control (`controllerchange`, with a guard flag to prevent a reload loop). `workbox.cleanupOutdatedCaches: true` was also added so a previous deploy's precached files get evicted once the new worker activates, instead of accumulating.
- **The manifest** (`name`, `short_name`, `theme_color`, icons, `display: 'standalone'`) is generated by the plugin, not hand-written as a static file — it's injected into `index.html` automatically at build time. `index.html` also manually carries an `apple-touch-icon` link and a `theme-color` meta tag, since iOS Safari's "Add to Home Screen" doesn't pick those up from the web manifest the way Android/Chrome does.
- **Two runtime-caching rules** (`workbox.runtimeCaching` in `vite.config.js`) are what make "offline-capable for viewed pages" literally true, not just an installable icon: (1) public `GET /api/*` requests — `NetworkFirst`, so a visitor online always gets fresh data, but a cached response from a previous visit serves instead of failing once offline. Explicitly excludes `/api/admin/*` and `/api/auth/*` by URL pattern so nothing authenticated ever lands in a cache a service worker could replay later. (2) image requests (`request.destination === 'image'`) — `CacheFirst`, since a meme's image rarely changes once posted. The precache (`globPatterns`) separately covers the built JS/CSS/HTML/icons, so the app shell itself opens offline too — together, a quiz/post/etc. a visitor already opened once will keep rendering with real data the next time they're offline, not just a blank shell.
- **PWA icons are hand-encoded PNGs, not drawn by an image library.** No image-processing tool was available in this dev environment (no `sharp`/`canvas` installed, and this Windows machine's `convert` on `PATH` resolves to the OS's NTFS-conversion utility, not ImageMagick — unsafe to invoke blind). `scripts/generatePwaIcons.mjs` renders the brand mark (gradient + two eyes + a smile, matching `favicon.svg`) pixel-by-pixel into a raw RGBA buffer, then encodes valid PNG files using only Node's built-in `zlib` (for the DEFLATE-compressed pixel data) plus a small hand-rolled CRC32 — no new dependency needed. Produces `icon-192.png`/`icon-512.png` (rounded corners, `purpose: 'any'`), `icon-maskable-512.png` (full-bleed, no transparent corners — required for Android's adaptive-icon masking), and `apple-touch-icon.png` (180x180, also full-bleed since iOS renders transparent corners as solid black). Re-run with `node scripts/generatePwaIcons.mjs` if the icon design ever changes.

### "📲 Add to Home Screen" button

The manifest/service-worker work above makes the site installable, but nothing ever surfaced that to a visitor — Chrome/Edge only show their own install affordance (an address-bar icon, or occasionally a browser-controlled mini-infobar) with no guarantee a visitor notices it. `useInstallPrompt.js` captures the browser's `beforeinstallprompt` event on mount (calling `preventDefault()` so the browser's own infobar never appears — nothing shows automatically at all) and holds onto it, since the event only fires once per page load and can only be used once. `Footer.jsx` renders a small "📲 Add to Home Screen" button next to the social icons, but only when `canInstall` is true — meaning the browser actually fired the event *and* the site isn't already running in standalone mode (checked via `matchMedia('(display-mode: standalone)')`/`navigator.standalone`). Clicking it calls the captured event's own `.prompt()`, which shows the browser's real native install dialog; the button then disappears (the prompt event is single-use either way, and an `appinstalled` listener also hides it permanently once actually installed). Deliberately just a quiet, permanent footer link rather than a banner/modal that appears and reappears — it never nags, and simply isn't there at all on browsers that never fire the event (iOS Safari, or a browser that already decided not to offer installability). Verified in the browser: confirmed the button stays hidden under normal conditions, then simulated a `beforeinstallprompt` event to confirm the button appears, clicking it calls the captured prompt, and the button correctly disappears afterward (a real prompt event can only be consumed once).

**Too subtle at first (fixed same day):** the initial style was an outlined `border-gray-300` button, matched to the footer's existing muted social-icon row — reported directly as too light to notice. Restyled to the same solid gradient (`bg-gradient-to-br from-violet-500 to-fuchsia-500`, white text) already used for the Achievements page's "📸 Share my level" button, so it reads as a real call-to-action rather than a faint outline easy to miss against the footer's other quiet links.

## Dark mode

Added 2026-07-31 on request ("fast, visible, broad appeal") — a manual light/dark toggle across the public site (admin panel is out of scope for this pass, since it was requested as a user-facing/GenZ-appeal feature).

- **Tailwind v4 class-based dark mode** — this project has no `tailwind.config.js` (CSS-only config via `@tailwindcss/vite`), so class-based dark mode needs a v4-specific `@custom-variant dark (&:where(.dark, .dark *));` line in `index.css` rather than the classic `darkMode: 'class'` config option. Every `dark:` utility class site-wide reads off whether `<html>` carries a `.dark` class.
- **`ThemeToggle.jsx`** (new) — a small sun/moon icon button, wired into `Header.jsx`. Toggling flips `.dark` on `document.documentElement` and persists the choice to `localStorage['twegle-theme']`.
- **No flash of the wrong theme on load** — a small inline `<script>` in `index.html`'s `<head>`, which runs synchronously before any CSS/JS loads, reads the saved preference (falling back to the OS-level `prefers-color-scheme: dark` media query if nothing's saved yet) and toggles `.dark` on `<html>` immediately — so the page never paints light and then snaps to dark a moment later.
- **Coverage** — every public page and shared component that renders plain gray-scale UI now carries `dark:` variants: `Header`/`Footer`/`ThemeToggle`, `Home`, `Quiz`/`Result`, `PostView`/`StoryView`, `FriendshipSetup`/`FriendshipPlay`/`FriendshipResult`, `CompareInvite`/`CompareResult`, `Game`/`TicTacToeMultiplayer`, `SearchResults`/`Browse`/`NotFound`, `About`/`Feedback`/`Privacy`/`Terms`, and shared components like `ProgressBar`/`AdSlot`/`ShareButtons`/`TileShareButton`/`ReportButton`/`PostCard` (meme branch). The colorful gradient tiles — `QuizCard`/`StoryCard`/`GameCard`/`FriendshipQuizCard`, quiz/story/compare-result gradient panels, and `PostCard`'s non-meme branch — needed no changes at all, since white text on a bright gradient already reads fine in either theme; `ShareSidebar` was already a dark `bg-gray-800` panel by design, likewise unaffected.
- Verified live: toggling actually switches every checked page with no console errors, the choice survives a full reload with no flash, and it persists via `localStorage`.

**Admin panel dark mode (added 2026-08-07):** originally deferred as internal-tool-only (see above), queued for later per the owner, and picked up this session. Reuses the exact same mechanism as the public site — the same `.dark` class, the same `ThemeToggle.jsx` component, and the same `twegle-theme` localStorage key, so a preference set on either side of the site carries over to the other. This required removing two guards that previously forced admin routes to always render light: `index.html`'s inline no-flash script had an `isAdmin` branch that skipped applying `.dark` on `/admin/*`, and both `Login.jsx` and `AdminLayout.jsx` had a `useEffect` that actively stripped the `dark` class on mount (added originally to prevent invisible white-on-white input text, back when admin had zero `dark:` styling at all). With every admin page now properly styled, both guards were counterproductive rather than protective, so both were deleted rather than worked around. `ThemeToggle` was added to `AdminLayout.jsx` in three places: the mobile top bar (next to the hamburger), the desktop sidebar footer (next to the admin's name/role, above Log out — visible whether the sidebar is collapsed or expanded), and nowhere on `Login.jsx` itself (no nav chrome there to put it in — an already-set preference still applies via the shared localStorage key). Every one of the panel's 22 components/pages (`AdminLayout`, `Login`, `Pager`, `StatusLabel`, `ProtectedRoute`, and all 17 admin pages — Dashboard, the 5 content-type List/Form pairs, Analytics, Activity, Feedback, Admins, Members/EndUserList, QuickAdd, BulkImport) got `dark:` variants added, following the same palette conventions already established on the public site (`dark:bg-gray-900`/`dark:bg-gray-800` for panels/inputs, `dark:text-gray-100`/`dark:text-gray-400` for primary/secondary text, `dark:border-gray-700`/`dark:border-gray-600`, and `dark:bg-<color>-950/40` + `dark:text-<color>-400` for colored badges/buttons like Delete or the "Needs a refresh" flag). Verified in the browser: toggled dark mode from both the mobile and desktop chrome, confirmed it persists across a full reload (including landing directly on `/admin/login` before authenticating), ran an automated luminance-contrast scan across Dashboard/QuizList/QuizForm/Analytics/Login in dark mode (only false positives — emoji glyphs and white text on the violet-600/gradient buttons and active nav links, the same expected pattern from the original public-site pass), confirmed form inputs render with a visible dark background and light text (the exact bug class the old light-only guard existed to prevent), and confirmed light mode still renders correctly afterward (no regression).
- **Bug fixed 2026-07-31: adding `ThemeToggle` shifted the search box's position.** `Header.jsx` originally laid out logo/search/(nothing) with a plain `flex justify-between`, where the search form (`flex-1 max-w-xs`) simply took whatever space was left after the logo — adding `ThemeToggle` as a third flex item changed how much space that was, visibly moving the search box. Fixed by switching the header row to a `grid grid-cols-[auto_1fr_auto]` layout (logo / search / toggle) with the search form centered (`flex justify-center`) inside its own middle track — the search box's position now only depends on the logo and toggle's own widths staying fixed, not on whichever elements happen to be neighbors, so it won't shift again if another icon is ever added to either side.
- **Bug fixed 2026-07-31: the initial dark-mode pass missed the 7 game engines entirely, breaking the site on any phone with system dark mode enabled.** Reported as "application not working properly in mobile browser, earlier it was working fine." Root cause: the no-flash script in `index.html` applies `.dark` based on the OS's `prefers-color-scheme` for anyone who's never explicitly toggled the switch — so a visitor whose phone defaults to dark mode (common on both Android and iOS) got the whole site's `.bg-dot-pattern` background switched to near-black (`#0f1115`) automatically, without ever touching the toggle. Every public page and shared component had been given `dark:` variants in the original pass, but the 7 actual game components in `src/games/` (`TicTacToe`, `RockPaperScissors`, `MemoryMatch`, `Game2048`, `WordGuess`, `GuessTheNumber`, `Sudoku`) were overlooked — only their `Game.jsx` wrapper page got dark treatment. These games render plain gray-scale UI (`text-gray-800` status lines, `bg-white` boards/tiles/buttons) with no `dark:` fallback, so on a dark-mode phone the status text became near-invisible (dark gray on near-black) and game boards looked visually broken against the dark page background — while the rest of the site (which does have `dark:` coverage) looked fine, making the games specifically read as "not working." Fixed by adding `dark:` variants to all 7 game files, matching the same treatment already given to `TicTacToeMultiplayer.jsx`. Verified via an automated contrast scan (comparing each leaf text node's color against its resolved background luminance) on Tic-Tac-Toe and Sudoku with `.dark` forced on — zero low-contrast text found afterward (previously flagged on every status line). This is also a good reminder that any future public-facing component needs the same `dark:` pass, not just top-level pages — a plain component with zero `dark:` classes doesn't error, it just silently renders in light-mode colors regardless of the page's theme, which reads as "half-fixed" rather than an obvious bug.
