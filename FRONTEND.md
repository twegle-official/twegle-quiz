# Frontend — What's Been Built

**Status:** Working — public site and admin panel both run against the real backend/database

## How to run it

```bash
cd frontend
npm install
npm run dev
```

Opens at whatever local address Vite prints (usually `http://localhost:5173`). Requires the backend to be running too (see `BACKEND.md`) — the frontend talks to it via `VITE_API_URL` in `.env` (defaults to `http://localhost:4000/api`).

## Shareable images (📸 Share as Image)

A plain link dies in a WhatsApp/Instagram Story — a real image gets reshared. Every quiz result and post now has a "Share as Image" button that generates a branded 1080×1920 (Story-ratio) PNG — emoji, title, description, and a "Twegle" logo badge, colored to match the quiz/category gradient — and either opens the phone's native share sheet (straight to Instagram Story/WhatsApp on mobile) or downloads the file (desktop, or browsers without file-sharing support).

- `src/utils/shareImage.js` — draws the card directly with the **Canvas 2D API** (`fillRect` for the gradient, `fillText` with manual word-wrapping for text, arc/text for the logo badge), then exports it with `canvas.toBlob()`.
- **Why not a DOM-screenshot library:** the first implementation used `html-to-image` (renders the DOM as an SVG `foreignObject`, loads that as an `<img>`, then draws it to canvas). That trick is a well-known source of cross-browser flakiness, and it hung indefinitely with no error at all during testing — confirmed down to a minimal red `<div>` failing the same way, ruling out anything specific to our card's content. Canvas 2D drawing has none of that fragility and is standard, reliable behavior on every browser, including mobile Safari — the primary target for this feature. `html-to-image` was removed from the project entirely.
- Gradient colors for canvas are a small hex lookup (`GRADIENT_COLORS` in `shareImage.js`) keyed by the same Tailwind gradient strings used everywhere else — keep it in sync if a new gradient is ever added to `gradients.js`.

## Link previews

`getQuizShareUrl`/`getPostShareUrl`/`getFriendshipShareUrl`/`getFriendshipResultShareUrl` in `api.js` build URLs pointing at the backend's `/api/share/...` routes rather than the React page itself — the "Copy link" and WhatsApp buttons in `ShareButtons` use whichever one is passed in as `url`. Full explanation of why (client-side apps can't set meta tags in time for link-preview crawlers) is in `BACKEND.md`. The "Share as Image" feature is unaffected by this — it shares an actual image file, not a link.

## SEO

A different problem from link previews above — Google's crawler does execute JavaScript and reads the rendered page, so unlike the WhatsApp/Instagram crawler problem, standard per-page `<title>` and meta description genuinely help here.

- **`src/utils/useDocumentMeta.js`** — a small hook (`useDocumentMeta(title, description)`) that sets `document.title` (as `"<title> | Twegle"`, falling back to the site default while data is still loading) and the `<meta name="description">` tag's content, resetting both back to the default on unmount. Wired into every content page: `Quiz`, `Result`, `PostView`, `Browse`, `FriendshipSetup`, `FriendshipPlay`, `FriendshipResult`, plus static titles on `About`/`Privacy`/`Terms`. No new dependency (no `react-helmet` or similar) — the app only ever needs to touch two tags, so a tiny hook does the job.
- **`Home.jsx`** renders minimal `WebSite` JSON-LD structured data (name, url, description) directly as a `<script type="application/ld+json">` — the one piece of structured data that actually fits cleanly; schema.org has no good native type for a personality-quiz result, so more elaborate structured data per quiz wasn't worth forcing in.
- **`frontend/public/robots.txt`** — a plain static file (allows all crawlers, blocks `/admin/`, points to the sitemap). Its `Sitemap:` line is a `https://yourdomain.com/...` placeholder since no real domain is registered yet — update it once one is (the sitemap directive must be a full absolute URL, not relative).
- **`VITE_SITE_URL`** (new env var, `.env`/`.env.example`) — the frontend's own public URL, used only for the `WebSite` schema's `url` field. Defaults to `http://localhost:5173` for local dev.
- **`sitemap.xml`** itself is generated by the *backend* (`GET /sitemap.xml`, not called by the frontend at all) since it needs live database content — see `BACKEND.md` for the generation logic and the one-time hosting rewrite it'll need once frontend/backend are on separate real domains.

## Friendship quizzes ("How well do you know me?")

The one genuinely new interaction pattern on the site — every other quiz type is single-player, this one is two-sided:

1. **`FriendshipSetup.jsx`** (`/friendship/:slug`) — fetches the question template, then a single-page form: a name field plus every question shown at once with tappable option buttons (not a multi-step wizard like the regular quiz flow — filling in known facts about yourself benefits more from being able to see/edit everything than from a dramatic one-question-at-a-time reveal). On submit, calls `createFriendshipInstance` and — without navigating away — swaps the same page into a "Your link is ready!" screen with `ShareButtons` pointed at the new shareable link.
2. **`FriendshipPlay.jsx`** (`/friendship/play/:code`) — a friend opens the link, sees the subject's name and the same questions (answers withheld by the backend, not just hidden in the UI), fills in their own name + guesses, and submits. On success, navigates to `/friendship/result/:attemptId` using the ID the backend just generated, so the result becomes a real, refreshable, shareable URL rather than transient state.
3. **`FriendshipResult.jsx`** (`/friendship/result/:attemptId`) — the score reveal: big `score/total`, a message that scales with how well they did, `ShareButtons` for posting their own score (which pulls more people back to the same `/friendship/play/:code` link — this loop is the actual growth mechanic), and a full per-question breakdown (✅/❌, what the subject picked, what the friend guessed).

`FriendshipQuizCard.jsx` is the homepage-tab card, linking to the setup page — separate from `QuizCard.jsx` since it shows a different stat ("N friends have guessed" instead of "N took this") and links to a different first step.

4 starter templates are seeded (2 English + 2 Hindi) via `npm run seed:friendship-quizzes` on the backend — see `BACKEND.md`.

## Compare with a friend (regular quizzes)

Brings the friendship-quiz's "share a link, friend plays too" growth loop to the regular single-player personality quizzes, without adding a new quiz-taking flow:

1. **`Result.jsx`** — after seeing their own result, a "🆚 Compare with a friend" button reveals an inline name field (same swap-the-page-in-place pattern as `FriendshipSetup.jsx`'s share screen); submitting calls `createQuizCompare` and shows a "Your link is ready!" panel with `ShareButtons`.
2. **`CompareInvite.jsx`** (`/quiz/:quizId/vs/:code`) — a friend opens the link and sees who invited them and which quiz, but **not** the first person's result (withheld server-side — see `BACKEND.md` — so it can't bias their answers). They enter their own name and tap "Take the Quiz," which navigates into the *existing* `Quiz.jsx` flow with the compare code/name passed via router state (`navigate(path, { state })`), so the actual quiz-taking UI is 100% reused, not duplicated.
3. **`Quiz.jsx`** — reads `location.state.compareCode`/`compareName`; on the last question, if a compare code is present, it submits the result to `joinQuizCompare` instead of navigating to the normal `/result/:quizId/:resultKey` page, then navigates to the reveal page. If the link turns out to be invalid/expired, it silently falls back to the normal result page rather than dead-ending the player.
4. **`CompareResult.jsx`** (`/quiz/:quizId/vs/:code/result`) — the reveal: both people's emoji/title side by side plus a match/no-match banner, `ShareButtons`, and an `AdSlot`. If opened before the friend has played (e.g. the first person checking back on their own link), shows a "Still waiting on your friend!" state instead. Opening an already-completed link's invite page (`CompareInvite.jsx`) auto-redirects straight here.

Reuses `generateUniqueCode`'s exact approach from the friendship-quiz feature (short random `code`, not a database ID) and the same `/api/share/*` link-preview pattern for WhatsApp/Instagram previews (`getQuizCompareShareUrl`).

## Non-personality (trivia) quizzes

Every quiz so far mapped answers to a personality result key, tallying which key got picked most. Trivia quizzes (`quiz.type === 'trivia'`) are right/wrong instead, scored numerically — built to reuse as much of the existing quiz-taking flow as possible rather than a parallel UI:

- **`Quiz.jsx`** — the same per-question `handleAnswer` and `scores` tally used for personality quizzes works unchanged for trivia, because a trivia option's `result` field is just the literal string `'correct'` or `'incorrect'` (see `BACKEND.md`) — so `scores.correct` already holds the right numeric score with zero new tallying code. The only real branch is at the *end*: `pickTriviaResult(quiz, scores)` finds whichever result's `minScore`-`maxScore` range contains the score, instead of `pickWinningResult` picking the most-tallied key. The score and question count are passed to the Result page via router state (`navigate(path, { state: { score, total } })`).
- **`Result.jsx`** — reads that router state to show "You scored X/N!" above the result title. Deliberately **not** load-bearing: a cold visit to a shared result link has no router state (it's only set by an in-app `navigate()` call), so the line simply doesn't render then — the result's own authored title/description still convey the tier either way, same graceful-degradation pattern already used for the compare-with-a-friend `compareCode`/`compareName` state.
- **`QuizForm.jsx`** (admin) — a new "Quiz Type" dropdown (Personality/Trivia) changes two things further down the same form: each answer option's "Pick result..." dropdown becomes a plain "Correct" checkbox (setting `result` to `'correct'`/`'incorrect'` directly), and each Result entry gains Min/Max score number inputs alongside the existing key/emoji/title/description fields. No separate trivia-authoring page — same form, same fields, just relabeled and re-typed based on the selected Quiz Type.

## Games

A new content type, but a different shape from Quiz/Post/FriendshipQuiz — a game isn't admin-authored data, it's code, so there's no admin CRUD and no fetch-by-slug from a database. Instead:

- **`src/games/registry.js`** — a plain static array (`{ slug, title, emoji, gradient, description }`), one entry per game. Adding a new game means adding an entry here, a component in `src/games/`, and a case in `Game.jsx`'s render switch — no backend or admin work required for the game itself.
- **`src/games/TicTacToe.jsx`** — the first game. Human is always X and always goes first; the AI (O) uses a full minimax search (small enough state space — 9 cells — to brute-force with no pruning) so it plays perfectly; the best a human can do is draw. Ties between equally-good AI moves are broken randomly so it doesn't always open the same way. The AI's move fires after a short delay so it doesn't feel instant. Calls `onGameEnd('win'|'loss'|'draw')` once when the board ends, and `onReset()` when "Play again" is clicked (letting the parent page clear its own end-of-game state — see the bug note below).
- **`src/games/RockPaperScissors.jsx`** — the second game. Deliberately uses a uniform-random AI pick rather than any "smarter" logic: a single round of RPS carries no information to exploit (unlike Tic-Tac-Toe, a solved perfect-information game), so random is the fair baseline, not a corner cut. Same `onGameEnd`/`onReset` contract as `TicTacToe.jsx`, so `Game.jsx` didn't need any changes beyond a registry entry and a render-switch case to support it.
- **`src/games/MemoryMatch.jsx`** — flip-and-match card pairs (6 emoji pairs, 12 cards). No adversary and no lose condition (untimed), so it only ever reports `onGameEnd('win')`, once all pairs are matched.
- **`src/games/Game2048.jsx`** — the standard 2048: a 4x4 grid, arrow-key or on-screen-button moves, tiles slide and merge via the well-known "transpose/reverse, then always slide left" trick (four directions reduce to one merge algorithm instead of four separate ones). Win at a 2048 tile, loss when the board is full and no direction changes it.
- **`src/games/WordGuess.jsx`** — a word-guessing game, deliberately named (and drawn) without any hangman/gallows imagery — just a shrinking heart/life counter — to stay consistent with the site's family-friendly tone. A small on-brand word list (TWEGLE, VIRAL, MEME, etc.), 6 lives, win on completing the word before lives run out.
- **`src/games/GuessTheNumber.jsx`** — "the house" picks a secret 1–100, the player gets higher/lower hints, 7 attempts (enough for a binary search over that range). A good example of a game with a real win/loss condition despite having no visible "opponent" to react to your moves.
- **`src/games/Sudoku.jsx`** — a 9x9 grid, medium difficulty (36 given clues). No puzzle database or backtracking solver needed: every puzzle starts from one closed-form solved grid (`((r*3 + Math.floor(r/3) + c) % 9) + 1`), then gets scrambled via the standard Sudoku symmetry operations — relabeling digits 1-9 with a random permutation, shuffling rows within each band of 3 and columns within each stack of 3, shuffling the 3 bands/stacks themselves, and a 50/50 transpose — all of which preserve the "each digit exactly once per row/column/box" property, so the result is always a genuinely valid, varied solved grid without ever needing to verify it. Blanking out 45 of the 81 cells (reusing the existing `shuffleArray` utility from `utils/shuffle.js`) produces the puzzle; solution-checking is a plain equality comparison against the grid used to generate it, not a general Sudoku validator. Live conflict highlighting (a cell turns red if its value duplicates another in the same row/column/3x3 box) uses a straightforward `hasConflict(grid, r, c)` check. No lose condition, same as Memory Match — only ever reports `onGameEnd('win')`, once every cell is filled and matches the solution. Supports both clicking a number-pad button and typing 1-9/Backspace on the keyboard once a cell is selected.
- **`Game.jsx`** (`/games/:slug`) — looks up the slug in the registry, renders the matching game component, and once it ends: records the anonymous outcome via `recordGamePlay`, shows `ShareButtons`, and an `AdSlot`. Share text is per-outcome and, since not every game frames itself as "beating the house" (a solo memory game or 2048 has no opponent to beat), per-game: a `SHARE_TEXT_OVERRIDES` map lets Memory Match/2048/Word Guess/Guess the Number/Sudoku supply their own win/loss phrasing, falling back to the original "beat the house" wording (`DEFAULT_SHARE_TEXT`) for Tic-Tac-Toe/Rock Paper Scissors, which are explicitly framed that way.
- **`GameCard.jsx`** — the homepage-tab card, styled identically to `QuizCard.jsx` ("N played" badge instead of "N took this"), fed by merging the static registry with `GET /api/games/counts` on the homepage.

**Bug caught during testing:** clicking "Play again" correctly reset the board, but `Game.jsx`'s own `outcome` state (which controls whether the share buttons show) didn't know the game had restarted, so the *previous* round's share buttons stayed visible over a fresh game. Fixed by having `TicTacToe` also call an `onReset` prop when the board clears, which `Game.jsx` uses to clear its own `outcome` state back to `null`.

## Two-player Tic-Tac-Toe

A real async match against a friend, separate from the single-player-vs-AI `TicTacToe.jsx` above — reached via a "🆚 Challenge a friend to a real match" link shown only on the Tic-Tac-Toe game page (`Game.jsx`, `game.slug === 'tic-tac-toe'`).

- **No accounts, so no server-side notion of "which browser is X."** Filling in the challenge form calls `createTicTacToeGame(name)`, which creates the match (the creator is always `X`) and immediately writes `localStorage['tictactoe-role-<code>'] = 'X'` *before* navigating to `/games/tic-tac-toe/:code` — that's the only place a role ever gets assigned as `X`. A friend opening the invite link has no such key yet, so `TicTacToeMultiplayer.jsx` shows a join form instead of a board; submitting it calls `joinTicTacToeGame` and writes `role = 'O'` the same way. From then on, revisiting that URL in that browser always resumes with the right role, no login needed.
- **Polling, not real-time.** There's no websocket infrastructure in this app, so while it's not your turn (including "still waiting for someone to join at all"), the page polls `GET /api/tictactoe/:code` every 4 seconds and re-renders when the state changes. This is a nice-to-have, not load-bearing — the game is genuinely *async*: closing the tab and checking back an hour later shows the real current state regardless of whether polling ever ran, same philosophy as the quiz-compare and friendship-quiz invite links.
- **Making a move** (`handleCellClick`) is guarded three ways before it even calls the API — a role must exist, the cell must be empty, and it must actually be that role's turn — then `makeTicTacToeMove(code, role, cell)` sends `{ role, cell }`, and the backend is the real authority on whether the move was legal (see `BACKEND.md`). If the request fails (most likely a timing race — the poll hadn't caught up with the opponent's move yet), the page just refetches the real state instead of showing a scary error.
- The board/status UI reuses the same 3x3 grid styling as the single-player `TicTacToe.jsx`, and `ShareButtons` at two different moments: while `status === 'waiting'` (send the invite), and once `status === 'finished'` (share the result, phrased from that browser's own role's perspective — "I beat Bob," "I drew with Bob," or "Bob beat me — think you can do better?").

## Stories

A new content type, modeled closely on Quiz rather than Post — its own model, own slug, own `/story/:slug` page — rather than reusing `Post`, since a story is one long body of prose with a proper shareable slug, not a short card.

- **`StoryView.jsx`** (`/story/:slug`) — fetches the story, shows the category/title in a gradient card matching `storyStyles.js`, the full body text below it, then `ShareButtons`, an `AdSlot`, a "You might also like" section (4 other stories, same-category-first, same shuffle-fallback pattern as `Result.jsx`/`PostView.jsx`), and a `ReportButton`.
- **"🔊 Listen to this story" / ⏸ Pause / ⏹ Stop** — a small `useReadAloud(text, language)` hook inside `StoryView.jsx` wraps the browser's built-in `SpeechSynthesisUtterance` (Web Speech API): `play()` cancels any in-flight utterance and starts a new one (`utterance.lang` set to `en-US`/`hi-IN` based on the story's language), `pause()`/`resume()` call the matching `speechSynthesis` methods, and a cleanup effect cancels speech on unmount so navigating away mid-narration doesn't leave it talking over the next page. If `'speechSynthesis' in window` is false (unsupported browser), the button is replaced with a plain "just read on below" note instead of throwing — voice availability varies by OS/browser, so this degrades gracefully rather than assuming it always works. No recorded voice, no paid TTS API, nothing server-side — the backend's only involvement is serving the story's `body` text (see `BACKEND.md`).
- **Bug fixed 2026-07-31: switching to a different story via "You might also like" left the previous story's narration still playing.** Reported directly. Root cause: React Router renders `/story/:slug` → `/story/:otherSlug` navigations by reusing the same `StoryView` component instance (just with new params/state), not a fresh mount — so the `useReadAloud` hook's cleanup effect, which was keyed only on `[supported]`, never re-ran when the story changed, only on actual unmount (leaving the site entirely). The new story's text loaded and rendered fine, but the old utterance kept talking, and the play/pause/stop button's `status` state didn't reset either, so it could show stale controls for narration that no longer matched the visible story. Fixed by re-keying the effect on `[supported, text]` instead: since `text` changes to the new story's body the moment it loads, React runs the previous render's cleanup (which cancels whatever was playing) before running the effect again for the new story (which resets `status` to `'idle'`) — the exact same cleanup-then-rerun mechanism already used for unmount, now also triggered by a same-component story swap. Verified in the browser: started narration on one story, clicked a different story from its suggestions, and confirmed `window.speechSynthesis.speaking` became `false` immediately and the button reset to "🔊 Listen to this story" rather than showing stale Pause/Resume controls.
- **`StoryCard.jsx`** — the homepage-tab/search-result card, styled like `QuizCard.jsx` (gradient background from `storyStyles.js`, a "🔊 Read & Listen →" pill instead of "Take the quiz →"), with the same `TileShareButton` every other card gets.
- **`storyStyles.js`** — per-category emoji/label/gradient (Horror/Comedy/Romance/Mystery/Moral Tales/Motivational), same pattern as `postStyles.js`.
- Homepage wiring (`Home.jsx`): a `storyCategory` filter (separate local state from `quizCategory`, since the two tabs have completely different category sets) drives its own row of category chips shown only on the Stories tab, and both category filters plug into the same tagged-content/scroll-reset machinery already built for quizzes (see "Known decisions" below).

A light, funny, entertainment-only horoscope feature — pulled forward from `PENDING_TASKS.md`'s backlog, placed as a homepage tab immediately after Stories per the request. Below that: the horoscope text itself, a small disclaimer line ("just for laughs — not real astrology, and definitely not medical/financial/legal advice"), `ShareButtons`, an `AdSlot`, and a link back home. ## Unified view/share engagement tracking

Post was the only content type with real view/share analytics (`recordPostEngagement`). Asked directly whether that gap also applied to Quiz, Friendship Quiz, and Games (it did — each only tracks completions, not views or shares), all four got the same tracking added in one pass via a single `recordEngagement(contentType, contentId, action)` call in `api.js`, rather than four separate near-identical helpers.

- **View** — fires once per page load (a `viewedRef` guard, same pattern `PostView.jsx` already used) on the page where that content is actually opened: `Quiz.jsx` (`recordEngagement('quiz', quiz._id, 'view')`), `FriendshipSetup.jsx` (`'friendshipQuiz'`), `Game.jsx` (`'game'`, using the game's slug as `contentId` since games have no database row), and `StoryView.jsx` (`'story'`).
- **Share** — fires via the `onShare` prop already supported by `ShareButtons.jsx`, wired onto that same page's share buttons: `Result.jsx`'s primary result share (not the separate "compare with a friend" share, which shares a different link entirely), `FriendshipSetup.jsx`'s "your link is ready" share, `Game.jsx`'s post-outcome share, and `StoryView.jsx`'s share. Tile-level shares (`TileShareButton` on `QuizCard`/`GameCard`/`StoryCard`/`FriendshipQuizCard`) aren't tracked — that component doesn't accept an `onShare` callback, same as it never did for Post either.
- **Admin side** — `fetchEngagementSummary(token, contentType)` in `adminApi.js` hits `GET /api/admin/engagement/:contentType`; `Analytics.jsx` renders one `EngagementTable` per type (Quiz/Friendship Quiz/Game/Story Engagement), reusing the exact column layout (title/Views/Shares) the existing Post Engagement table already used.

## Share before attempting

Every share button on the site used to be tied to *after* finishing something — a quiz result, a friendship-quiz score, a game outcome, or opening a post. There was no way to invite a friend to anything before either of you had opened it. Built once as a shared component, then wired into **every** content tile: `QuizCard.jsx`, `GameCard.jsx`, `PostCard.jsx` (jokes/funny lines/quotes/motivational quotes/memes), `StoryCard.jsx`, and `FriendshipQuizCard.jsx` all show the same small 🔗 icon in the card's corner.

- **`TileShareButton.jsx`** (new shared component, `frontend/src/components/`) — takes `{ title, shareUrl, shareText }` and renders the icon plus a floating popover (Share/WhatsApp/Copy link). Every card passes its own item-specific `shareUrl`/`shareText`, so sharing any tile always previews *that specific* quiz/game/joke/meme/friendship quiz, never a generic site-wide link. Each card's `shareUrl` points at a crawler-friendly backend `/api/share/*` route (see `BACKEND.md`) built from that item's own title/description:
  - Quiz → `getQuizIntroShareUrl(slug)` → `GET /api/share/quiz/:slug`
  - Game → `getGameShareUrl(slug)` → `GET /api/share/game/:slug` (new — games have no database row, so the backend keeps a small `GAME_META` map mirroring `games/registry.js`, same duplication pattern as `GAME_SLUGS` already used for play-tracking)
  - Post (joke/funny line/quote/motivational quote/meme) → `getPostShareUrl(post._id)` → `GET /api/share/post/:id` — this route already existed (built for the individual `/post/:id` page's own share buttons) and needed no changes; the tile just reuses it
  - Friendship Quiz → `getFriendshipQuizIntroShareUrl(slug)` → `GET /api/share/friendship-quiz/:slug` (new — shares the *template* before anyone's filled it in, distinct from the existing instance/result share routes)
  - Story → `getStoryShareUrl(slug)` → `GET /api/share/story/:slug`
- **The popover is `absolute`, not part of the card's normal flex flow.** A first version (built for `QuizCard.jsx` only, before this was generalized) rendered it as a plain block between the description and the action pill, which pushed that pill down and made one card visibly taller than its row-mates whenever its popover was open — breaking the equal-card-height invariant documented under "Known decisions" below. Floating it above the content instead (`position: absolute`, anchored to the icon) fixes this: opening/closing the popover never changes the card's own height.
- **The popover's buttons are plain `<button>`s, not `<a>` tags**, even for WhatsApp (which normally is a real link elsewhere in the app, e.g. `ShareButtons.jsx`). Every one of these cards is itself a real `<Link>` (so ctrl-click/right-click "open in new tab" and crawlers still work) — nesting an `<a>` inside another `<a>` is invalid HTML and breaks click behavior, so the WhatsApp button instead does `window.open(waUrl, '_blank', 'noopener,noreferrer')` from a plain button. Every handler also calls both `preventDefault` and `stopPropagation`, since the popover sits inside the card's own `<Link>` and a click needs to reach the button without also navigating into the item underneath it. Closes automatically on an outside click (a `mousedown` listener attached only while open).

## "You might also like" suggestions

`Result.jsx`, `PostView.jsx`, and `StoryView.jsx` all end with 4 suggested-next cards (`QuizCard`/`PostCard`/`StoryCard`, same components used everywhere else, so they look identical to the homepage grid) instead of just a bare "take another quiz"/"see more" link — 4 rather than 3 so the 2-column grid (see below) fills evenly as a 2×2 block instead of leaving one card alone on its own row. Fetches everything in the same language, prefers items in the same category as the current one, shuffles within each group (`src/utils/shuffle.js`) and falls back to other categories if there aren't enough same-category items, then takes the first 4 — so a small content library (e.g. only 2 posts in one category) never breaks. No new backend endpoint — reuses the existing `fetchQuizzes`/`fetchPosts`/`fetchStories` list calls, filtering out the current item client-side.

**Bug fixed 2026-07-31: cards were badly cramped in this section.** All three of these pages are narrow single-column reading pages (`max-w-xl`, 576px), but the suggestion grid was `sm:grid-cols-3` — the same 3-column count used on the wide homepage grid (`max-w-6xl`, 1152px). Squeezed into the narrower page, each card landed at only ~170px wide, and `QuizCard`/`StoryCard`'s bottom-row badge (`"Take the quiz →"` / `"🔊 Read & Listen →"`) had no `whitespace-nowrap`, so its text wrapped internally across 3-4 lines instead of staying on one line — ballooning card height (up to ~340px) and visually overlapping the category label next to it. Fixed two ways: the grid is now `sm:grid-cols-2` on all three pages (giving each card ~264px, plenty of room), and `whitespace-nowrap` was added to every card's bottom-row badges (`QuizCard`, `StoryCard`, and — proactively, since they have the exact same pattern — `GameCard`/`FriendshipQuizCard` too, even though neither is used in a suggestions section yet) so the wrap can't recur if a card ever ends up in an even narrower spot. `SUGGESTION_COUNT` was also bumped from 3 to 4 right after, once the 2-column grid made 3 items look lopsided (2 cards on one row, 1 alone on the next) — 4 fills a clean 2×2 block instead. Verified via computed `getBoundingClientRect()` measurements in the browser: story suggestion cards went from 332px tall (badge wrapped to 112px) down to 208px tall (badge a clean single-line 32px), same improvement confirmed on quiz and post suggestions; confirmed all three pages render exactly 4 suggestion cards after the count change.

## Search

`Header.jsx` (rendered once for the whole public site, not per-page) now carries a search box alongside the logo. Submitting navigates to `/search?q=<query>` (`SearchResults.jsx`), which calls the new `GET /api/search` endpoint and groups whatever comes back into up to three sections — Quizzes, Friendship Quizzes, and Jokes/Quotes/etc. — reusing `QuizCard`/`FriendshipQuizCard`/`PostCard` so results look identical to browsing the homepage. The header's input syncs itself from the URL's `?q=` (via a `useEffect` on `useSearchParams()`), so landing on a search results page (whether by submitting the form or opening a shared search link) shows the active term and lets you refine it without retyping — and clears itself again once you navigate to an unrelated page.

## Memes

Not a new page type or model on the frontend either — memes are `category: 'meme'` posts, reusing the exact same admin CRUD, homepage tab, and `/browse/:category` machinery every other post category already had. Two things are genuinely different:

- **`PostCard.jsx`** (new, shared by `Home.jsx` and `Browse.jsx` — previously each had its own near-identical inline card markup) renders a meme as an actual `<img>` with an optional caption underneath, instead of the colored gradient+text card every other category gets. This is also where the tile-height fix lives (`h-full flex flex-col`, same reasoning as `QuizCard.jsx`).
- **`PostView.jsx`** shows the image full-size for a meme, and swaps the "📸 Share as Image" canvas-generation button for a plain "⬇️ Download Image" link pointing straight at `post.imageUrl` — generating a synthetic branded card doesn't make sense here (there's no text to lay out, the meme already *is* the shareable image), and drawing an arbitrary external image onto a `<canvas>` runs into CORS restrictions most image hosts don't lift, so a direct download link is both simpler and more reliable.

**Admin side:** `PostForm.jsx` shows an "Image URL" field instead of a required "Text" field when Category is set to Meme (text becomes an optional caption), and `PostList.jsx` shows a small thumbnail preview next to meme rows so admins don't have to open each one to see what it is.

**Why paste-a-URL instead of a real upload** — see `BACKEND.md`'s "Memes" section; short version: no file storage exists yet, and a naive server-disk upload would silently stop working the first time this deploys to most hosts. 6 starter memes are seeded (3 English + 3 Hindi) using placeholder images from Lorem Picsum (royalty-free, made for exactly this kind of use) — swap for real meme images any time via the admin panel.

## Admin panel — what it does right now

Reachable at `/admin/login` (no link from the public site — admins go there directly). `AdminLayout.jsx` uses a **left sidebar nav** (logo, Quizzes/Posts/Stories/Friendship Quizzes/Analytics/Activity/Feedback/Admins links — each now paired with an emoji, e.g. "🎯 Quizzes" — user info + logout) at `lg:` and up — sticky, full-height, room to grow the nav list without recrowding — falling back to a simple stacked top bar below `lg` (same responsive strategy as the public site's `Home.jsx` filter sidebar: a flex row that just stacks in DOM order on narrow screens, nav first then content, rather than a separate mobile nav component). Originally a single top bar; moved to a sidebar because the top bar was already tight on one line (6 nav links + user info + logout) and a sidebar is the more standard admin-panel layout anyway. **Collapsible** on desktop: a small circular toggle button straddles the sidebar's right edge (`‹`/`›`), shrinking it to a 64px icon-only rail (emoji only, labels hidden) or expanding it back to the full 224px version with labels — the choice persists across page loads via `localStorage`. ## How data flows now

## Known decisions worth knowing about

- `react-router-dom` has open security advisories in npm's audit database, but every one is about server-rendering / server-action features this app does not use (we're a plain client-side Vite app — only `BrowserRouter`, `Routes`, `Route`, `Link`, `Navigate`). Worth re-checking `npm audit` occasionally as new versions ship.
- **Quiz card colors must come from `src/gradients.js`, never free text.** Tailwind generates CSS by scanning literal class name strings in the source code at build time — it cannot see class names that only exist as data from the API/database at runtime. This caused a real bug (cards showing no color at all) once quiz data moved from a source file to the live database. The fix: a fixed palette lives in `gradients.js` as literal strings Tailwind can see, and the admin panel's "Card Color" dropdown only ever picks from that list — never accepts typed-in values. When adding new quiz topics needs more colors than are safelisted, add the new gradient string to this file first — see `BACKEND.md`'s bug #3 for the same lesson applied to the `language` field (new fields need backfilling on old data, new gradients need safelisting before use). Post category colors in `postStyles.js` reuse gradients already safelisted here, so no changes were needed there.
- **`ShareButtons` takes an optional `shareText` prop now**, instead of always deriving share copy as `` `${title} — take the quiz!` ``. Needed once the component started getting reused for friendship-quiz links and score reveals, where "take the quiz!" read oddly tacked onto "How well do you know Ashish?" or "I scored 6/8...". Passing `shareText` overrides the default; every other caller (quiz results, posts) is unaffected since the prop is optional.
- **The Clone feature's generated title needs a unique tag, not just a static `"(Copy)"`.** Found while testing Clone on a Hindi-titled quiz: the backend's slug generator only keeps Latin/numeric characters, so a Hindi title contributes nothing to the slug — only the English `"(Copy)"` suffix survived, meaning every clone of every Hindi quiz collided on the same slug (`copy`). Fixed on both sides: the clone title now includes a short random tag (`(Copy a1b2)`), and the backend's slug generator has its own fallback for titles that reduce to nothing at all — see `BACKEND.md`'s bug #5 for the full story.
- **`ShareButtons`'s "Copy link" handler must not let a failed clipboard write silently swallow the share-tracking call.** Found while testing post-share analytics: `navigator.clipboard.writeText()` can throw ("Write permission denied") in contexts without clipboard permission — notably in-app browsers like Instagram/TikTok's, which is exactly where this app's traffic is expected to come from. Since the original code did `await navigator.clipboard.writeText(url)` before firing the `onShare` callback, a denied clipboard permission meant the share was never counted at all, with no visible error. Fixed by wrapping the clipboard call in its own try/catch so `onShare?.()` always fires on click, regardless of whether the copy itself succeeded.
- **`QuizCard`/`FriendshipQuizCard` need `h-full flex flex-col` on the card itself, not just on the grid wrapper.** Found from a real report: card tiles in the same row were visibly different heights. `Home.jsx` wraps each card in a `<div>` that (correctly) stretches to fill its CSS Grid row, but the `<Link>` inside — the actual colored card — had no explicit height, so it only grew to fit its own content, leaving an unstyled gap below shorter cards while the wrapper silently stretched around it. Fixed by making the `Link` itself `h-full flex flex-col` with `mt-auto` on the bottom action row, so every card in a row now fills the same height and the "Take the quiz"/"Fill it in" pill lines up at the same vertical position regardless of how long the title/description is. The inline post cards (jokes/quotes/etc.) in `Home.jsx` didn't have this bug — they're the direct grid item with no extra wrapper, so CSS Grid's default `align-items: stretch` already sized them correctly.
- **Admin list pages must not debounce their very first load.** Found from a real report of the admin panel "flickering" when switching between Quizzes/Posts/etc. `QuizList.jsx` and `PostList.jsx` fire `load()` inside `setTimeout(load, 250)` so typing in the search box doesn't send a request per keystroke — but that same 250ms delay was also applied to the initial mount, meaning every single navigation to either page guaranteed at least 250ms of a bare "Loading..." state before the real content ever appeared, even though the request itself resolves in well under 50ms locally. Fixed with an `isFirstRender` ref: the first run of the effect calls `load()` immediately, and only subsequent filter/search changes get debounced.
- **The hero band's quiz/post counts are fetched, not hardcoded.** They used to be a literal `"24 quizzes"` / `"85+ jokes & quotes"` string in `Home.jsx`, manually edited (and easy to forget) every time new content shipped. Now a one-time `useEffect` fetches `GET /api/quizzes` and `GET /api/posts` with no language filter (both endpoints return every language when the param is omitted) and counts them client-side (non-meme posts only, matching the "jokes & quotes" wording), with the old hardcoded numbers kept only as a same-value fallback shown for the brief moment before the fetch resolves.
- **When rendering content that depends on which tab/filter is active, tag the fetched data with what it was fetched for — don't just clear-and-refetch and trust that timing works out.** `Home.jsx` used to call `setItems(null)` in a `useEffect` after `activeTab` changed, but React still renders once with the *new* `activeTab` and the *old* `items` before that effect runs. Switching from Quizzes to Jokes could momentarily render quiz objects through the post-card code path (which reads `post.category`, undefined on a quiz) — a full crash if a `.gradient` property gets read off that undefined lookup. Fixed by storing fetched results tagged with the tab/language that produced them (`{ tab, language, items }`) and only trusting `items` when that tag matches the current `activeTab`/`language` — otherwise it shows the loading state instead of stale data. Worth reusing this pattern anywhere content is fetched per-tab/per-filter.
- **A `transition-[width]` utility on a `position: sticky` flex item can leave the computed width visibly stuck at the old value after a class change, in this dev environment at least.** Found while building the collapsible admin sidebar: toggling between `lg:w-16`/`lg:w-56` updated the element's `className` correctly (confirmed via DevTools) and worked fine on a fresh page load, but a same-session React state toggle left `getComputedStyle(...).width` reporting the *previous* value indefinitely — not a transition timing issue (waited well past any reasonable duration). A plain test element with the same class, added fresh to the page, picked up the correct width immediately, meaning the utility itself wasn't broken — something about applying it to *this specific* sticky flex item was. Removed the transition entirely rather than chasing the exact cause further, since an instant width snap was an acceptable trade for a working toggle. Worth avoiding `transition-[width]` on sticky elements here until/unless this gets properly root-caused.
- **Bug fixed 2026-07-31, then reworked the same day: clicking a homepage filter visibly yanked the sticky sidebar out of place, not just scrolled the content.** First attempt clamped `Home.jsx`'s scroll-reset to never go past the results grid's top (`Math.min(currentScrollY, contentTop)`, via a `preScrollRef` captured synchronously in every filter's `onClick`, applied through `setTimeout(fn, 0)` rather than `requestAnimationFrame` since this environment's headless preview tab doesn't reliably fire rAF callbacks — confirmed separately via a failed screenshot and a timed-out rAF polling loop). That technically kept the sidebar's on-screen position unchanged for content-rich tabs, but landed at a *different* offset per tab depending on how much content that tab had (a content-sparse tab like Memes never let the sidebar get "stuck" in the first place) — reported back as still not fixed, since the inconsistency across tabs read as more confusing than a single predictable behavior. Reworked to a plain, unconditional `window.scrollTo(0, 0)` on every filter/tab change instead — every click now lands at the exact same place (hero, sidebar, and content all visible together from the top) regardless of which tab or how much content it has, trading "sidebar never visually moves" for "behavior is always identical and predictable," which is what was actually being asked for. The `preScrollRef`/`selectFilter`/`contentRef` machinery from the clamped attempt was removed entirely.
- **Trending/Newest sort toggle generalized to every homepage tab, not just Quizzes.** Previously the sort toggle only rendered (and only worked) on the Quizzes tab. Now every tab — Friendship Quiz, Memes, Games, Stories, Jokes, Quotes, Funny Lines, Motivational — shows the same toggle and sorts real data: quizzes/games sort "Trending" by `totalPlays`, friendship quizzes by `totalAttempts`, and everything else (posts, stories) by a new `totalEngagement` field (views+shares aggregated server-side from the existing `PostEngagement`/`Engagement` models, mirroring the aggregation already used for quiz play counts) as a popularity fallback since those content types have no "completion" concept. "Newest" sorts by `createdAt` for everything with a real creation date; Games (which are code, not database rows, so they have no `createdAt`) approximate it by reversing the static games registry, whose order roughly matches when each game actually shipped.
- **Trending/Newest moved next to the language switcher.** Requested directly: since Trending/Newest is a "global filter" like language (applies the same way regardless of which tab is active), it didn't make sense to bury it at the bottom of the sidebar, below the tab-specific category chips. Moved it to sit immediately after the EN/हिंदी toggle, before the tabs row — the sidebar now reads as "global filters first (language, sort), then content-type-specific filters (tabs, category chips)" instead of mixing the two.
- **Homepage tab order: Funny Lines now immediately follows Jokes**, ahead of Quotes and Motivational Quotes — grouping the two quick one-liner formats together. New order: Quizzes, Friendship Quiz, Memes, Games, Stories, Jokes, Funny Lines, Quotes, Motivational Quotes.

## PWA support (installable, offline-capable for viewed pages)

Not a native app — a plain web app that can be installed to a phone's home screen and keeps working (for content already viewed) without a connection, via `vite-plugin-pwa` (Workbox under the hood).

- **`vite.config.js`** — the `VitePWA()` plugin config. `registerType: 'autoUpdate'` means a new deployed version takes over silently on the next load, no user-facing "update available" prompt (kept simple for now). `devOptions: { enabled: true }` lets the service worker actually run under `npm run dev`, not just a production build — otherwise "does this work" could only ever be answered after a full build+preview cycle.
- **The manifest** (`name`, `short_name`, `theme_color`, icons, `display: 'standalone'`) is generated by the plugin, not hand-written as a static file — it's injected into `index.html` automatically at build time. `index.html` also manually carries an `apple-touch-icon` link and a `theme-color` meta tag, since iOS Safari's "Add to Home Screen" doesn't pick those up from the web manifest the way Android/Chrome does.
- **Two runtime-caching rules** (`workbox.runtimeCaching` in `vite.config.js`) are what make "offline-capable for viewed pages" literally true, not just an installable icon: (1) public `GET /api/*` requests — `NetworkFirst`, so a visitor online always gets fresh data, but a cached response from a previous visit serves instead of failing once offline. Explicitly excludes `/api/admin/*` and `/api/auth/*` by URL pattern so nothing authenticated ever lands in a cache a service worker could replay later. (2) image requests (`request.destination === 'image'`) — `CacheFirst`, since a meme's image rarely changes once posted. The precache (`globPatterns`) separately covers the built JS/CSS/HTML/icons, so the app shell itself opens offline too — together, a quiz/post/etc. a visitor already opened once will keep rendering with real data the next time they're offline, not just a blank shell.
- **PWA icons are hand-encoded PNGs, not drawn by an image library.** No image-processing tool was available in this dev environment (no `sharp`/`canvas` installed, and this Windows machine's `convert` on `PATH` resolves to the OS's NTFS-conversion utility, not ImageMagick — unsafe to invoke blind). `scripts/generatePwaIcons.mjs` renders the brand mark (gradient + two eyes + a smile, matching `favicon.svg`) pixel-by-pixel into a raw RGBA buffer, then encodes valid PNG files using only Node's built-in `zlib` (for the DEFLATE-compressed pixel data) plus a small hand-rolled CRC32 — no new dependency needed. Produces `icon-192.png`/`icon-512.png` (rounded corners, `purpose: 'any'`), `icon-maskable-512.png` (full-bleed, no transparent corners — required for Android's adaptive-icon masking), and `apple-touch-icon.png` (180x180, also full-bleed since iOS renders transparent corners as solid black). Re-run with `node scripts/generatePwaIcons.mjs` if the icon design ever changes.

## Dark mode

Added 2026-07-31 on request ("fast, visible, broad appeal") — a manual light/dark toggle across the public site (admin panel is out of scope for this pass, since it was requested as a user-facing/GenZ-appeal feature).

- **Tailwind v4 class-based dark mode** — this project has no `tailwind.config.js` (CSS-only config via `@tailwindcss/vite`), so class-based dark mode needs a v4-specific `@custom-variant dark (&:where(.dark, .dark *));` line in `index.css` rather than the classic `darkMode: 'class'` config option. Every `dark:` utility class site-wide reads off whether `<html>` carries a `.dark` class.
- **`ThemeToggle.jsx`** (new) — a small sun/moon icon button, wired into `Header.jsx`. Toggling flips `.dark` on `document.documentElement` and persists the choice to `localStorage['twegle-theme']`.
- **No flash of the wrong theme on load** — a small inline `<script>` in `index.html`'s `<head>`, which runs synchronously before any CSS/JS loads, reads the saved preference (falling back to the OS-level `prefers-color-scheme: dark` media query if nothing's saved yet) and toggles `.dark` on `<html>` immediately — so the page never paints light and then snaps to dark a moment later.
- **Coverage** — every public page and shared component that renders plain gray-scale UI now carries `dark:` variants: `Header`/`Footer`/`ThemeToggle`, `Home`, `Quiz`/`Result`, `PostView`/`StoryView`, `FriendshipSetup`/`FriendshipPlay`/`FriendshipResult`, `CompareInvite`/`CompareResult`, `Game`/`TicTacToeMultiplayer`, `SearchResults`/`Browse`/`NotFound`, `About`/`Feedback`/`Privacy`/`Terms`, and shared components like `ProgressBar`/`AdSlot`/`ShareButtons`/`TileShareButton`/`ReportButton`/`PostCard` (meme branch). The colorful gradient tiles — `QuizCard`/`StoryCard`/`GameCard`/`FriendshipQuizCard`, quiz/story/compare-result gradient panels, and `PostCard`'s non-meme branch — needed no changes at all, since white text on a bright gradient already reads fine in either theme; `ShareSidebar` was already a dark `bg-gray-800` panel by design, likewise unaffected.
- **Admin panel is intentionally untouched** in this pass — it's an internal tool, not part of the "kids/teens/GenZ appeal" surface the toggle was requested for.
- Verified live: toggling actually switches every checked page with no console errors, the choice survives a full reload with no flash, and it persists via `localStorage`.
- **Bug fixed 2026-07-31: adding `ThemeToggle` shifted the search box's position.** `Header.jsx` originally laid out logo/search/(nothing) with a plain `flex justify-between`, where the search form (`flex-1 max-w-xs`) simply took whatever space was left after the logo — adding `ThemeToggle` as a third flex item changed how much space that was, visibly moving the search box. Fixed by switching the header row to a `grid grid-cols-[auto_1fr_auto]` layout (logo / search / toggle) with the search form centered (`flex justify-center`) inside its own middle track — the search box's position now only depends on the logo and toggle's own widths staying fixed, not on whichever elements happen to be neighbors, so it won't shift again if another icon is ever added to either side.
- **Bug fixed 2026-07-31: the initial dark-mode pass missed the 7 game engines entirely, breaking the site on any phone with system dark mode enabled.** Reported as "application not working properly in mobile browser, earlier it was working fine." Root cause: the no-flash script in `index.html` applies `.dark` based on the OS's `prefers-color-scheme` for anyone who's never explicitly toggled the switch — so a visitor whose phone defaults to dark mode (common on both Android and iOS) got the whole site's `.bg-dot-pattern` background switched to near-black (`#0f1115`) automatically, without ever touching the toggle. Every public page and shared component had been given `dark:` variants in the original pass, but the 7 actual game components in `src/games/` (`TicTacToe`, `RockPaperScissors`, `MemoryMatch`, `Game2048`, `WordGuess`, `GuessTheNumber`, `Sudoku`) were overlooked — only their `Game.jsx` wrapper page got dark treatment. These games render plain gray-scale UI (`text-gray-800` status lines, `bg-white` boards/tiles/buttons) with no `dark:` fallback, so on a dark-mode phone the status text became near-invisible (dark gray on near-black) and game boards looked visually broken against the dark page background — while the rest of the site (which does have `dark:` coverage) looked fine, making the games specifically read as "not working." Fixed by adding `dark:` variants to all 7 game files, matching the same treatment already given to `TicTacToeMultiplayer.jsx`. Verified via an automated contrast scan (comparing each leaf text node's color against its resolved background luminance) on Tic-Tac-Toe and Sudoku with `.dark` forced on — zero low-contrast text found afterward (previously flagged on every status line). This is also a good reminder that any future public-facing component needs the same `dark:` pass, not just top-level pages — a plain component with zero `dark:` classes doesn't error, it just silently renders in light-mode colors regardless of the page's theme, which reads as "half-fixed" rather than an obvious bug.
